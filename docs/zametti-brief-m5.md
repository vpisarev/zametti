# Zametti — бриф для Claude Code, этап 5: арена IR

## Контекст

Этапы 1–4 закрыты. Оптимизация разбита владельцем на **два этапа**:

- **этап 5 (этот бриф)** — только арена IR: представление данных ядра;
- **этап 6 (отдельный бриф, здесь не делается)** — кэш документов, декод
  картинок в размере показа, инкрементальный патч через префикс/суффикс-diff.
  Что в него войдёт — зафиксировано в конце этого документа, чтобы решения
  не потерялись и не переизобретались.

Обязательное чтение: предыдущие брифы и отчёты, `zametti-core-notes.md`,
`zametti-editor-notes.md`, текущий `ir.h`.

В отличие от этапа 4, **ядро менять можно и нужно** — но при жёстком условии:
**наблюдаемое поведение не меняется ни на байт**. Это этап представления, не
семантики.

## Цель этапа

1. IR на арене: один сплошной буфер текста + плоские массивы, блоки и спаны —
   POD со смещениями. Ноль аллокаций на блок/спан.
2. Отчёт-замер «до/после».
3. Аудит чёрного ящика: полный список мест, знавших про внутренности IR.

## Не-цели

- всё содержимое этапа 6 (см. конец): кэш документов, кэш/декод картинок,
  префикс/суффикс-diff, инкрементальный патч QTextDocument;
- история/журнал заметок;
- любые изменения канона, сериализации, разбора — байты на диске и в выводе
  неприкосновенны;
- три давних красных фаззера — остаются в своём состоянии;
- побочные рефакторинги «раз уж залезли» — нет.

## Первая задача: замер «до»

Подменный аллокатор со счётчиком (двадцать строк, глобальный `operator new` в
тестовом бинарнике). Прогнать: полный корпус (271 заметка); один большой файл
5–10 МБ (взять из сети реальные большие markdown — спецификации, книги;
положить в `.testdata/big/`); синтетика — файл с десятками тысяч коротких
спанов. Снять: число аллокаций, время parse, время поиска по IR в памяти,
пиковый RSS. Все числа — в отчёт; тем же пробником потом снимается «после».

## Структуры

```cpp
struct Range {                      // полуоткрытый [start, end), как cv::Range
    int32_t start = 0, end = 0;
    bool empty() const { return start >= end; }
    int32_t size() const { return end - start; }
};

struct Inline {                     // бывший Span; словарь CommonMark
    Range   text;                   // байты в Document::chars
    Range   href;                   // пустой = нет ссылки; при image — путь
    Range   title;                  // пустой = нет; только при image
    uint8_t flags = 0;              // Bold|Italic|Strike|Code|Image|Comment
};

struct Block {                      // POD, без владения
    Kind     kind = Kind::Paragraph;
    Marker   marker = Marker::Bullet;
    bool     checked = false;
    bool     raw = false;           // true → text это дословные байты,
                                    //         остальные поля игнорируются
    int8_t   headingLevel = 0;
    HtmlKind html = HtmlKind::Comment;
    int16_t  level = -1;
    Range    text;                  // байты в Document::chars
    Range    info;                  // байты в Document::chars; пустой = нет
    Range    inlines;               // ИНДЕКСЫ в Document::spans, не байты
};

struct Document {
    NoteMeta meta;                  // не меняется: она крошечная
    std::string chars;              // единая арена: текст, raw-куски, href, info
    std::vector<Inline> spans;
    std::vector<Block>  blocks;
    // доступ и запросы — методами, см. ниже
};
```

Принятые решения (не пересматривать без разговора с владельцем):

- **Никаких side-таблиц.** Ни `image_id`+map, ни `infomap`: href — это прежде
  всего обычные ссылки, а не только картинки; единый механизм «всё переменной
  длины — Range в арену» дешевле и проще любых карт. `Document` остаётся
  тривиально копируемым: memcpy четырёх буферов.
- **`rawSource` исчезает**: `bool raw` переключает интерпретацию `text`.
  Отдельного raw-буфера нет — арена одна.
- **Два координатных пространства**: `Block::text`/`info` и `Inline::*` —
  байты в `chars`; `Block::inlines` — индексы в `spans`. Перепутать — баг.
  Дисциплина: в `validate()` проверяются границы обоих пространств
  (все Range внутри своих массивов, `inlines` не пересекаются между блоками,
  байтовые Range в пределах `chars`).
- **`int32` в Range достаточно**: заметка > 2 ГБ не входит в модель мира;
  `validate()` может это утверждать при разборе.

## API: методы Document

Всё, чему нужен доступ к арене или к соседям, — методы `Document`
(решение владельца):

```cpp
std::string_view text(const Block&)  const;   // при raw — дословные байты
std::string_view info(const Block&)  const;
std::string_view text(const Inline&) const;
std::string_view href(const Inline&) const;
std::string_view title(const Inline&) const;
std::span<const Inline> inlines(const Block&) const;
bool wouldMerge(const Block& prev, const Block& next) const;
bool isClosedHtmlComment(const Block&) const;
void validate() const;              // debug-ассерты, расширить границами Range
```

`isOrdered`/`isTask` арены не читают — могут остаться свободными функциями от
`Block&`. Возвращаемые `string_view` живут не дольше `Document` — IR
транзиентен, но правило записать в комментарий к классу.

## Построение и мутация

- IR **иммутабелен после постройки**. Строят два места — парсер и reader, —
  оба через builder-интерфейс `Document` (append-only: добавить блок, дописать
  байты, получить Range).
- Перед разбором — `chars.reserve(len(source) * k)`: суммарный текст + raw +
  href не превышает источник существенно; коэффициент k подобрать замером на
  корпусе (ожидается ~1.0–1.2) и записать в отчёт. Цель — ноль реаллокаций
  арены на разборе, проверяется счётчиком.
- Единственный известный мутатор — переписывание ссылок при импорте:
  **replace-by-append** (новые байты в хвост арены, Range перенаправляется;
  старые байты остаются мусором — для транзиентного IR это норм). Арена
  grow-only, смещения не протухают никогда.
- Builder МОЖЕТ уже в этом этапе считать по-блочный хеш, если это одна строка;
  использовать его будет этап 6.
- Проверить и записать в отчёт: существует ли где-нибудь IR-to-IR склейка
  (перенос блоков между двумя Document). Ожидание — нет: фрагменты клипборда и
  move-item — одноразовые конвейеры. Если найдётся — остановиться и обсудить.

## Аудит чёрного ящика — деливерабл

Смена типов полей превращает компилятор в аудитора: **полный список мест, не
скомпилировавшихся после замены, — обязательная секция отчёта**, с пометкой у
каждого «читал текст / мутировал / конструировал литерал». Ожидаемые:
сериализатор, builder (QTextDocument), reader, поиск, сниппеты, json_dump,
переписывание ссылок в импорте, литералы IR в тестах, свободные функции из
самого `ir.h`. Интересно, что всплывёт сверх списка.

Литералы в тестах переводятся на builder — это единственная разрешённая
правка тестов; **ожидаемые значения тестов не меняются ни на байт**.

## Инварианты и тесты

```
A. Поведение не меняется: все существующие наборы зелёные без правки ожиданий
   (три известных красных фаззера — в прежнем состоянии)
B. Разбор корпуса и большого файла: ноль реаллокаций арены, аллокаций на
   блок/спан нет (счётчик)
```

Новые тесты:

- builder: Range-границы, пустые Range (нет href/info), raw-блок,
  replace-by-append не ломает существующие Range;
- `validate()`: оба координатных пространства, выход за границы ловится в
  debug;
- независимость копии `Document`: скопировать, дописать в оригинал —
  копия не изменилась;
- замер «после» тем же пробником — таблица «до/после» в отчёте:
  аллокации, parse, поиск в памяти, RSS.

## Этап 6 — зафиксировано здесь, НЕ делается в этом этапе

Решения согласованы с владельцем, бриф будет отдельный; записаны, чтобы не
переизобретать:

- **Замер картинок как первая задача этапа 6**: счётчик и время декодов в
  `loadResource`; сценарий — заметка с 20–30 картинками ~3 Мп (профиль
  владельца), открыть → уйти → вернуться.
- **Кэш документов, а не картинок**: LRU из последних 8–16 собранных
  `QTextDocument`. Возврат в недавнюю заметку — ноль пересборки и ноль
  декодов; **undo переживает переключение заметок** (стек живёт в документе) —
  это отдельный критерий приёмки.
- **Декод в размере показа** (ширина колонки × dpr, вёдрами по ширине) — нужен
  в любом случае: полные декоды 30 × 3 Мп держали бы ~360 МБ на документ, кэш
  из восьми таких — гигабайты.
- **Отдельный байтовый LRU пикселей — только по замеру**, если документный кэш
  не покрывает паттерн (дорогое переоткрытие вытесненного, одно вложение во
  многих заметках).
- **Инкрементальный патч**: diff старого и нового IR плоским общим
  префиксом/суффиксом по арене (memcmp POD-блоков и срезов; по-блочные хеши —
  если builder их уже считает), подмена диапазона блоков публичным
  `QTextCursor` (`findBlock` — O(log N), замена — undoable-правка). Приватные
  внутренности `QTextDocument` не трогаются никогда: хирургия в обход курсора
  ломает undo. Критерий корректности — логический:
  `reader(патченный) == reader(пересобранный)`.

## Исследование для этапа 6 (только отчёт, ничего не менять)

Задокументировать в отчёте: как builder представляет многострочные блоки (код,
raw-куски) в `QTextDocument` — по `QTextBlock` на строку или одним блоком с
`U+2028` (`QChar::LineSeparator`)? Выполняется ли сегодня равенство
`doc.blockCount() == blocks.size()` (соответствие 1:1 IR-блок ↔ QTextBlock)?
Если нет — на каких родах ломается. Это входные данные для этапа 6
(инкрементальность стоит на 1:1); в этом этапе ничего не менять.
