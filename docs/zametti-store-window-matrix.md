## Контекст

Владелец назвал две живые боли и один диагноз:

1. **«Reset password» немедленно перезаливает всё** (69 МБ, ~2 минуты) при
   застывшей строке статуса — окно выглядит мёртвым.
2. **После перезаливки снова спрашивают пароль**, хотя он был введён за минуту
   до этого.
3. **Код кривой**: corner-кейсы всплывают по одному, хотя при честной модели
   большая часть разруливалась бы сама.

**Поправки владельца, вшитые ниже:**

- **П1.** `Open selected` не запрещается на уже открытом хранилище: жест просто
  закрывает окно. Погашенная кнопка там — «ненужный заёб программы».
- **П2.** **Диалог не делает ничего долгого. Никогда.** Строка «идёт работа»
  исчезает из матрицы навсегда. Всё длинное — фоновая работа со статус-баром,
  пока человек правит заметки.
- **П3.** Пароли, лежащие в связке, показываются В ПОЛЕ кружочками — как
  настоящие. Глаз будит связку (мастер-пароль ОС / Touch ID, по её политике) и
  показывает настоящий пароль.
- **П4.** Пустая папка + пустое удалённое хранилище + пароль (`EW*EP`) —
  законный случай: «завести новое здесь и сразу подружить с сервером». После
  `Check` честно говорим, что там пусто, — **обычным шрифтом, не красным**.
  Кнопка `Open selected` в этом случае становится `Create`, как и в `EL`.
- **П5.** **Кнопка `Check` остаётся `Check`.** Отдельного «Disconnect» нет:
  очисткой удалённого хранилища занимается вторая кнопка, переименованная в
  **`Reset cloud`**, и переспрос у неё с тремя дорогами:
  `The cloud storage "name" will be erased. Proceed?`
  `[Erase & change encryption password] [Erase & disconnect] [Cancel]`.
- **П6.** **`Download` в диалоге не существует.** Диалог только устанавливает
  связь. Скачиванием занимается обработчик `open`: он видит, что синк нужен,
  берёт самую свежую заметку (можно без картинок), открывает её — и остальное
  везёт фоном, пока человек читает и правит.
- **П7.** **Формулировки в диалоге — сильно короче.** Абзацев в статусе не
  бывает (словарь строк — §1.9).
- **П8.** **Окно выше:** видны сразу два состояния — локального хранилища и
  удалённого. `X` → `Local: neither a zametti storage nor an empty folder`,
  `M` → `Local: missing directory`; в обоих `Open selected` погашена.

# §0. ТЕРМИНОЛОГИЯ: ОДНО СЛОВО ВМЕСТО ДВУХ

Сегодня в коде живут ОБА слова, и граница между ними случайна: `remoteConfig`
хранит адрес, а `hasCloud()` спрашивает, есть ли он; `connectRemote`
подключает, а `probeCloud` разведывает; `makeRemote` строит адаптер, а
`cloudHasKeyfile` дёргает тот же адаптер. Это ровно тот сорт беспорядка, из
которого растут corner-кейсы: два слова заставляют думать, что сущности две.

**Побеждает `cloud` — решение владельца.** Слово выбрано то, которым владелец
думает («локальное облако в виде папки» — его формулировка про каталог-облако),
и оно же остаётся в глазах пользователя. Цену за это платит код: `remote`
сегодня многочисленнее и сидит в трёх местах, до которых обычное переименование
не достаёт, — и каждое из них названо ниже отдельной строкой, чтобы ни одно не
проехало молча.

| было | стало | замечание |
|---|---|---|
| `RemoteStore` | `CloudStore` | адаптер-транспорт |
| `WebDavRemote` · `FolderRemote` · `MemoryRemote` · `PlainRemote` | `WebDavCloud` · `FolderCloud` · `MemoryCloud` · `PlainCloud` | `FolderCloud` — слово самого владельца |
| `remote_store.*` · `webdav_remote.*` · `folder_remote.*` · `fake_remote.*` | `cloud_store.*` · `webdav_cloud.*` · `folder_cloud.*` · `fake_cloud.*` | **файлы**: `git mv`, CMake, `compile_commands.json` перегенерировать |
| `Config::remoteUrl` · `remoteDir` · `remoteUser` | `cloudUrl` · `cloudDir` · `cloudUser` | **имена полей в JSON** — см. миграцию ниже |
| **`remote.json`** | **`cloud.json`** | **формат на диске** — см. миграцию ниже |
| CLI `set-remote` | `set-cloud` | **командная строка**; старое имя остаётся псевдонимом на одну версию |
| `remoteConfig()` | `cloudConfig()` | |
| `Config::hasCloud()` | `Config::hasCloudAddress()` | «адрес назван» — не то же, что «подключено» |
| `ZStorage::hasRemote()` | `ZStorage::isConnected()` | «адаптер подключён сейчас»; сегодня эти два вопроса названы похоже и оттого путаются |
| `makeRemote` · `setRemote` · `dropRemote` | `makeCloud` · `setCloud` · `dropCloud` | |
| `connectRemote` · `attachRemote` · `useLastRemote` · `initFromRemote` | `connectCloud` · `attachCloud` · `useLastCloud` · `initFromCloud` | |
| `writeRemoteConfig` · `clearRemoteConfig` | `writeCloudConfig` · `clearCloudConfig` | |
| `remoteEtag` · `kRemoteName` · `remotePlain` · `healedRemote` | `cloudEtag` · `kCloudName` · `cloudPlain` · `healedCloud` | |
| `probeCloud`/`CloudProbe`, `cloudHasKeyfile`, `mintIfCloudEmpty`, `cloudNotes/Attachments/Bytes` | без изменений | уже названы правильно |
| `resetCloudEncryption` | `eraseCloudStorage` + `initCloudStorage` (§2.6) | распадается на две честные двери — слово владельца |
| строки UI | `Cloud (WebDAV)`, `Cloud: …`, кнопка `Reset cloud`, `The cloud storage "…" will be erased.` | §1.9 |

**Миграция формата — единственное место, где переименование стоит кода.**
`remote.json` лежит В КАЖДОЙ копии хранилища (у владельца их несколько, и не
все обновятся в один день), поэтому:

- чтение: сперва `cloud.json`, при его отсутствии — `remote.json`; поля тоже с
  оглядкой (`cloudUrl`, иначе `remoteUrl`);
- запись: всегда `cloud.json`, и старый файл удаляется тем же атомарным шагом,
  каким пишется новый;
- файл ЛОКАЛЬНЫЙ (в облако не уезжает, в журнал не попадает), так что
  разъехавшиеся версии друг другу не мешают: старая копия просто продолжает
  читать своё имя;
- `docs/info/zametti-storage.md` правится ТЕМ ЖЕ коммитом (правило проекта);
- тест: хранилище со старым именем читается, после первой записи имя новое,
  старого файла нет, а содержимое совпало.

Правится **по LSP, а не sed'ом** (правило проекта): переименование символа —
вопрос к `rename`/`findReferences`. Тремя коммитами, без единой правки
поведения: символы ядра → файлы и CMake → формат и CLI с миграцией.

Дальше по документу — только `cloud`.

# §1. МАТРИЦА

## 1.1 Обозначения

**Zero** — список хранилищ пуст.

Остальное — четырёхбуквенный код + буква жеста через дефис:

| Место | Что | Буквы |
|---|---|---|
| 1 | **локальная папка** (по ПОЛЮ пути, не по строке) | **E** пустая · **V** хранилище zametti · **M** папки нет (переехало) · **X** непустая и не хранилище |
| 2 | **удалённое хранилище** (по полям формы) | **W** названо (webdav-сервер; каталог-remote считаем ему равнозначным) · **L** не названо, хранилище живёт чисто локально |
| 2′ | **пароль СЕРВЕРА** — строчный хвостик у `W`, пишется когда важен | **Ww** набран в поле · **Wk** поле пусто, пароль лежит в связке · **Wh** поле пусто и в связке нет — связываться нечем |
| 3 | **что на сервере НА САМОМ ДЕЛЕ** | **E** пусто · **V** наше хранилище (манифест + конверт) · **X** чужое или неполное. При `L` — прочерк `-` |
| 4 | **чем открывать удалённое** | **P** пароль набран в поле · **K** поле пусто, ключ хранилища лежит в связке · **N** поле пусто и ключа нет |
| жест | кнопка | **+** · **−** · **B** browse «…» · **C** check · **R** reset remote · **O** open selected / create · **X** close |

Модификатор **`o`** — эта строка и есть ОТКРЫТОЕ сейчас хранилище (`VWkVKo`);
возможен только при первой букве `V`.

**Симметрия нарочная:** у пароля сервера ровно те же три состояния, что у
пароля шифрования (`P`/`K`/`N` ≡ `Ww`/`Wk`/`Wh`) — набран, лежит в связке, нет
нигде. Показывать их надо одинаково (§1.2).

**ВАЖНО: третья буква — это ПРАВДА О СЕРВЕРЕ, а не знание программы.** До
нажатия `C` программа её не знает, поэтому **доступность кнопок от третьей
буквы не зависит никогда** — от неё зависит только ИСХОД `C`. Это же
объясняет, почему «свежесть» нельзя держать глобальным флагом окна: она
свойство пары «адрес + время последней проверки».

**Вырожденные сочетания** (в матрице их нет):

- `K` и `Wk` требуют `V`: записи в связке лежат под `storeId`, а `storeId` есть
  только у хранилища. У `E`/`M`/`X` ответ связки всегда «нет» — оттого
  скачивание на новом устройстве и спрашивает всё с клавиатуры;
- `o` требует `V`;
- при `L` третья буква — прочерк, а четвёртая ни на что не влияет.

## 1.2 Связка ключей: как её видно (П3)

Связка — **такая же ось состояния, как папка и сервер**, и она обязана быть
видна, не спрашивая.

### Различить — не читая секрета

Новая дверь у `SecretStore`, симметричная для обоих секретов:

```cpp
bool hasKey(const QString& storeId);              // ключ шифрования
bool hasServerPassword(const QString& storeId);   // пароль webdav
```

Проверка СУЩЕСТВОВАНИЯ записи без чтения секрета. Это не педантизм:
сегодняшние `loadKey`/`serverPassword` читают данные (`kSecReturnData`,
`keyring_secrets_keychain.cpp:168`), а чтение на маке имеет право поднять
системный вопрос связки — звать его на каждое переключение строки нельзя,
иначе программа начнёт спрашивать пароль сама, ровно в духе жалобы №2. Запрос
одних атрибутов (`kSecReturnAttributes` без `kSecReturnData`; в libsecret —
поиск без загрузки секретов) вопроса не поднимает. **Проверяется пробником на
маке ДО реализации** — `tests/keyring_probe.cpp` уже есть, туда и добавить.

### Показать — кружочками в поле, одинаково для обоих паролей

| состояние | поле | глаз |
|---|---|---|
| набран (`P` / `Ww`) | набранное под точками | доступен: показать набранное |
| **в связке** (`K` / `Wk`) | **кружочки, как у настоящего пароля** | доступен: **будит связку** (мастер-пароль ОС / Touch ID) и показывает настоящий |
| нет нигде (`N` / `Wh`) | пусто; placeholder КРАСНЫМ `not on this device` | погашен — показывать нечего |
| ключ в связке, пароля нет (хранилище до третьей записи) | пусто; placeholder СЕРЫМ `not on this device` — облаку хватает ключа | погашен — показывать нечего |

Кружочки и глаз считаются от ОДНОЙ записи связки — той, где пароль (правка
31.08): прежняя грамматика «кружочки про ключ, глаз про пароль» рисовала
кружочки-обещание при мёртвом глазе у всякого хранилища, подключённого до
появления третьей записи.

Кружочки — **подстановка, а не значение**: модель держит при поле признак «это
заглушка связки», наружу её никогда не отдаёт (в работу уходит либо набранное,
либо секрет из связки), и первое же нажатие клавиши в поле заглушку стирает —
дальше поле обычное. Ровно так ведут себя браузеры с сохранённым паролем, и
человек этот язык уже знает.

## 1.3 Долгих работ в диалоге не бывает (П2)

**Правило:** окно хранилищ — место, где НАЗЫВАЮТ данные, а не место, где ждут.
Всё, что дольше вздоха, принадлежит фоновой работе со статус-баром, которая уже
умеет и прогресс, и отмену, и повтор.

Следствия:

1. Строка «идёт работа» **исчезает из таблицы доступности навсегда**. `Close`
   доступен всегда: окно закрывается, даже если проверка ещё в полёте (её исход
   тогда просто некому показать — работа бросается, ничего не портя).
2. В диалоге остаются работы **порядка секунды**: листинг (`C`), разворот
   конверта (Argon2id ~1.5 с — порог владельца), чеканка конверта, несколько
   запросов к серверу. Поля на это время гаснут, статус говорит, что
   происходит, и всё.
3. **Стирание удалённой копии — фоновая работа, а не диалог.** Это важно и не
   очевидно: у `RemoteStore` пять операций и среди них нет «удалить каталог»
   (`remote_store.h:78` — только `del(name)`), значит стереть 445 объектов =
   445 запросов. Поэтому стирание делится надвое (§1.6): диалог сносит ГОЛОВУ
   (манифест + конверт — два запроса, после них удалённое уже «не хранилище»)
   и уходит; хвост сметает фоновая работа со счётчиком и отменой. Прерывание
   безопасно в любой точке: голова снесена первой.

## 1.6 Таблица C — жест `R` = `Reset cloud` (П2, П5)

Кнопка живёт только на `VW***` и только после попытки `C` по этому адресу.
Смена строки и правка адреса гасят её до новой проверки (сегодня не гасят ✗!).

### Переспрос — один, с тремя дорогами

Санкционированное исключение из «никаких диалогов подтверждения»: операция
деструктивна.

```
The cloud storage "mynotes" will be erased. Proceed?
[Erase & change encryption password]  [Erase & disconnect]  [Cancel]
```

**Когда ключ под рукой (`K` — связь удалась ключом из связки), первая дорога
стирания не требует** и переспрос честнее звучит иначе:

```
Change the encryption password for "mynotes"?
[Change password]  [Erase & disconnect]  [Cancel]
```

**Когда `C` не достучался** (сервер молчит, логин отвергнут) — стирать нечего
и нечем; остаётся местная дорога:

```
The server does not answer. Forget it? The remote copy stays as it is.
[Disconnect]  [Cancel]
```

### Дорога 1a: `[Change password]` — `VW**K`, ключ под рукой

Ничего не разрушается, и потому нечего стирать:

1. `Keyfile::rewrap(_, new, params)` на ключе из связки — новая соль, новый
   nonce, ТОТ ЖЕ мастер-ключ (старый пароль не нужен: ключ уже разбужен);
2. залить ОДИН конверт (килобайты);
3. секреты — в связку.

Перезаливки нет **ни у одного устройства**: движок уже умеет ротацию конверта и
прямо оговаривает случай «смена ПАРОЛЯ перезаписывает keyfile, не меняя ключа»
(`sync_ops.cpp:1149`) — другое устройство увидит новый etag, вскроет пробный
журнал тем же ключом и поедет дальше.

Говорим: `Password changed.`

### Дорога 1b: `[Erase & change encryption password]` — `VW**N`, ключ забыт

Конверт не развернуть по построению — удалённую копию приходится пересоздавать.
**Но диалог этим не занимается.** Он делает мгновенную часть и уходит:

1. проверка «наше или безымянное» (манифест) — чужое не трогаем;
2. `eraseCloudStorage` **головой вперёд**: манифест и старый конверт (два
   запроса) — после них удалённое уже не хранилище ни для кого;
3. `initCloudStorage`: чеканка конверта из нового пароля и его заливка;
4. локальная бухгалтерия синка стирается: её метки — про блобы, которых больше
   нет;
5. секреты — в связку; адрес — в `remote.json`.

**Четыре запроса вместо 445.** После них состояние ПОЛНОСТЬЮ ЭКВИВАЛЕНТНО «мы
только собрались залить локальное хранилище первый раз»: конверт наш, манифеста
нет, бухгалтерии нет — а «нет манифеста» ядро и так трактует как первый синк.

Хвост старой копии (осиротевшие блобы, зашифрованные потерянным ключом; имена
выводятся из ключа, поэтому новая заливка их не перекроет) сметает **фоновая
работа** — тем же прогоном, что заливает заново, со счётчиком и отменой.

Говорим: `Erased. Uploading in the background.`

### Дорога 2: `[Erase & disconnect]` — уйти совсем

Ответ владельца на вопрос «кто сметает осиротевшие блобы»: **эта опция сметает
всё**. Мгновенная часть в диалоге:

1. проверка «наше или безымянное»;
2. голова (манифест + конверт) — два запроса;
3. `clearRemoteConfig` + `dropRemote`; три записи из связки — вон;
4. хвост — фоновой работе `eraseCloudStorage`, со счётчиком в статус-баре.

Говорим: `Disconnected. Erasing in the background.`

Локальное хранилище цело и работает дальше как чисто локальное (`VL`).

  мгновенно) — для диалога; полное, с `progressDone/Total` и `cancel`, — для
  фоновой работы. Голова первой ВСЕГДА: прерывание не должно оставить нечто,
  похожее на целое хранилище. Чужой манифест — отказ до единого удаления.
- **`ZStorage::initCloudStorage(cfg, password, serverPassword, secrets,
  mintParams, outcome, error)`** — чеканка конверта, его заливка, адрес в
  `remote.json`, секреты в связку, локальная бухгалтерия синка обнулена.
  Мгновенно. Она же закрывает **M**: `VW*EK` — не «Connected» в никуда, а
  честный конверт (или честная просьба о пароле).
- **`ZStorage::changeEncryptionPassword(cfg, newPassword, serverPassword,
  secrets, mintParams, error)`** — `Keyfile::rewrap` на ключе из связки,
  заливка ОДНОГО конверта. Ничего не стирает и не перезаливает.

`resetCloudEncryption` остаётся для CLI —
владелец сказал, что метод нужен, — но становится тонкой композицией
`eraseCloudStorage(full)` + `initCloudStorage` + `pushAll`. Одна дорога, три
ступени, и у каждой ступени есть свой вызывающий.

## 2.7 Секреты и молчуны (боль 2; беды C, D)

Одна дверь укладки секретов на все ветки (connect, create, erase, change):
ключ + пароль сервера + пароль шифрования; отказ связки — **словами в статус**,
не в `stderr`.

## 2.8 Фоновая работа стирания

`SyncController` учится второй работе: `startErase(cfg)` — хвост после головы,
со счётчиком, отменой и повтором, теми же, что у синка. Без неё
`[Erase & disconnect]` некому доделать.

## 2.9 Первый прогон: свежая заметка первой (П6)

Порядок материализации первого прогона: самая свежая заметка → её открыть →
остальные тексты → вложения. Это работа движка синка, не диалога; отдельный
коммит и отдельный тест (первое открытие показывает заметку раньше, чем
скачаны картинки).

## 2.10 Санитарная

`store_manager_dialog.cpp` — только раскладка и исполнение (цель брифа);
`store_manager_dialog_test.cpp` худеет до интеграции модель↔виджеты↔поток.

# §3. ТЕСТЫ

`tests/store_manager_model_test.cpp` — без виджетов, с фиктивными исходами
работ. **Имя и комментарий каждого случая — код клетки**, чтобы тест и документ
читались друг через друга:

```
// VW*EK-C: хранилище, адрес назван, на сервере ПУСТО, ключ в связке,
// пароля не ввели. Беда M: сегодня говорим «Connected», а конверт не
// уезжает — другое устройство увидит «incomplete». Ждём: просьбу о пароле,
// а по нему — отчеканенный и залитый конверт.
```

Обязательный зоопарк:

1. `Zero` — две живые кнопки, слова вместо молчания; опустевший список чистит
   поля (**G**).
2. `+`: `V` / `E` / `X` / дубль.
3. `−`: обычная, `*o` (немедленное отцепление), отказ.
4. **Таблица A целиком** одним табличным тестом: код клетки → ожидаемая маска
   доступности семи кнопок И подпись `O` (`Open selected`/`Create`). Одна
   таблица в тесте против одной таблицы в документе. Отдельной строкой —
   `V****o-O` доступна и просто закрывает окно (**Q**), `M`/`X` погашены
   (**П8**), `X` доступен всегда (**H**).
5. **Таблица §1.9 целиком** вторым табличным тестом: код клетки → обе строки
   фактов и их цвет. Здесь ловится **R** (`EW*EP` — `Cloud: empty` НЕ красным)
   и **T** (сообщение отдельно от фактов, и оно в одну строку — тест меряет
   длину и запрещает `\n`).
6. Ветки таблицы B: `VW*EN-C`, `VW*VN-C`, `VW*XN-C`, `VW*VK-C`, `VW*EK-C`
   (**M**), `VW*EP-C`, `VW*VP-C`, `EWwVP-C` (связь БЕЗ скачивания — **S**),
   `EWwEP-C`, `MWwVP-C`, `XW***-C` (**K**), `*Wh**-C` (**P**), `VL-C` погашена
   (**П5**).
7. Автомат свежести целиком: пусто → повтор → несовпадение → совпадение →
   подключение; **залипание после чеканки** (тот же адрес второй раз — пароль
   один); смена адреса забывает свежесть; **переключился на другую строку и
   вернулся — факты строки те же** (**F**).
8. `VW*VP-C` с неверным паролем → связь доказана → `R` загорается (**E**).
9. `VW**K-R`: переспрос называет `[Change password]`; работа — `rewrap`,
   **стёрто 0 объектов, залит 1 конверт**, старый пароль конверт больше не
   открывает, новый открывает (**A**).
10. `VW**N-R` → `[Erase & change encryption password]`: в диалоге **ровно
    четыре запроса** (два удаления головы, заливка конверта, запись адреса),
    манифеста нет, бухгалтерия снесена, **блобы никто не заливал и не стирал**
    — а состояние сервера совпадает с состоянием «перед первой заливкой»
    (**B**, П2).
11. `VW**-R` → `[Erase & disconnect]`: голова снесена, адрес и три секрета
    забыты, хвост отдан фоновой работе; локальное хранилище живо и стало `VL`.
12. `VW**-R` при недостучавшемся `C`: переспрос показывает только
    `[Disconnect]`; удалённое не тронуто.
13. После `R` любой дороги — **три секрета в связке**; отказ связки виден в
    статусе (**C, D**).
14. `V****-O` переезд: черновик едет за строкой, адрес не теряется (**I**).
15. `EW*EP-O` (`Create`): локальное заведено, конверт залит, окно закрылось,
    заливка отдана фону (**П4**). `EW*VP-O` (`Create`): идентичность из
    манифеста, **ни одного скачанного блоба в диалоге** (**S**, П6).
16. **Связка видна и не спрашивается** (**J, O, P**): `VWk*K` — ни одного
    красного требования, в обоих полях кружочки-заглушки, **оба глаза доступны
    при «пустых» полях**; `VWh*N` — оба требования красные, глаза погашены; во
    всех этих снимках модель зовёт `hasKey`/`hasServerPassword` и НИ РАЗУ не
    читает секрет (счётчик чтений поддельной связки = 0); заглушка НИКОГДА не
    уезжает в работу как пароль.
17. `EWh*N-O` и `EWh*N-C` — сказано, чего именно не хватает (**N, P**).

В ядре (`tests/remote_store_test.cpp`):

- `changeEncryptionPassword` меняет пароль, не трогая блобы: число объектов то
  же, следующий `sync` ничего не заливает, другое устройство после ротации
  продолжает работать своим ключом;
- `eraseCloudStorage(headOnly)` + `initCloudStorage` + обычный прогон дают
  ровно то же, что и первая заливка с нуля (сравнение листингов), и прерывание
  между ступенями безопасно;
- `eraseCloudStorage(full)` на ЧУЖОМ манифесте не удаляет ни одного объекта;
- `resetCloudEncryption` (CLI) = композиция трёх ступеней и даёт тот же
  результат, что и раньше.

# §5. ЧТО РЕШЕНО СЛОВОМ ВЛАДЕЛЬЦА

Семь вопросов, заданных двумя редакциями, закрыты:

1. **Подпись `C`** — остаётся `Check` (П5). Отвязка ушла из `C` целиком: у неё
   теперь своё место в переспросе `Reset cloud`.
2. **Кто сметает осиротевшие блобы** — `[Erase & disconnect]` сметает всё, а
   стирание головой вперёд делает хвост безопасным мусором, который добирает
   фоновая работа (§2.8). Отдельного права «синк стирает лишнее» заводить не
   пришлось.
3. **Судьба `resetCloudEncryption`** — метод нужен; он вырождается в
   композицию `eraseCloudStorage` + `initCloudStorage` + `pushAll` и живёт
   для CLI (§2.6).
4. **`Open selected` на `M`/`X`** — погашена, и рядом сказано почему (П8).
5. **Одно слово** — `cloud` (§0). Цена названа там же построчно.
6. **`Reset cloud` на строке с пустой папкой** (`EW***`) — **не заводим**.
   Случай «хочу вычистить сервер и начать с пустого места» владелец закрывает
   руками: заходит на сервер и чистит папку. Кнопки, живущей ради редкого
   случая и умеющей стирать чужое, не будет.
7. **Пустое поле при живом ключе** — значит «возьми ключ из связки» (§1.2).
   Стёртые кружочки паролем не считаются и в работу не уезжают; забыть ключ
   можно только через `Reset cloud`. Владелец согласился попробовать этот
   вариант — значит, за ним следят: если в живой работе он окажется
   двусмысленным, это идёт в отчёт, а не замалчивается.
