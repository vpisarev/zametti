# Документация заметками: папка Info и метка `access: read-only`

Отчёт о сессии 26.08.2026, третья часть дня.

Итог одной строкой: **документация уехала из окна «о программе» в дерево
заметок — виртуальной папкой `Info`, которую заводит `ZStorage`, — а защищает
её не запрет в окне, а метка `access: read-only` в шапке, наследуемая от папки
вниз.**

## 1. Решения владельца

1. Окно «About» — **две вкладки**: «чьё это и из чего собрано» и «Licenses».
   Читать длинный README в диалоге 760×620 неудобно; вдобавок у вкладки не было
   масштаба вовсе — `markdownPage` не звал `setZoom`, и текст всегда шёл в
   базовом кегле. Отсюда и жалоба «текст маленький».
2. В левой колонке — **виртуальная папка `Info`** со значком `lucide:badge-info`,
   на уровне корня, **последней строкой**, видимая даже когда хранилища нет.
3. Внутри — вшитые документы, **только для чтения**, читаются как обычные
   заметки.
4. Облик страницы — **обычный фон заметки**, не серый, как у архива: это не
   отложенное добро, а текст, который просто не правят.
5. **У `ZStorage` должен быть метод добавления виртуальной папки** — чтобы
   дальше всё работало на автомате, а не особыми случаями в окне.
6. **`access: read-only` в метаданных заметки и папки**; read-only у папки —
   read-only у всего внутри. Тогда защита папки Info не пишется отдельно.
7. Поиск по хранилищу (`Ctrl+Shift+F`) в Info пока не ходит.
8. Сборка — **`-j8`** вместо `-j4`.
9. Впереди — **ввоз книжек (fb2 и другие)**; книжки read-only. Метка делается
   не ради справки: её главный потребитель — настоящие заметки в хранилище.

## 2. Что сделано

### 2.1 Ядро: метка доступа

`NoteHeader::kAccessKey` / `kReadOnlyValue`, `readOnly()`/`setReadOnly()` — по
образцу `archived`: свой ключ и ничего кроме, `modified` не трогается (пометка
доступа не правка содержимого). Неизвестное значение — **не ошибка**: заметка
считается правимой, ключ в файле не трогается, о непонятом сказано в stderr.

`ZNote::isReadOnly()/setReadOnly()`, `ZNote::Metadata::readOnly()` — там же, где
`archived`.

`ZStorage::isReadOnly(id)` — подъём по родителям, ТОЧНАЯ КОПИЯ `inArchive`,
включая защиту от цикла. Заслоны стоят:

| глагол | что делает |
|---|---|
| `rewriteNote` | отказ + строка в stderr; **одна дверь**, и через неё идут `rename`, `move`, `setSortMark`, пометка архива |
| `remove` | отказ: замок, переживающий удаление, — не замок |
| `archive` | отказ: архивация переписывает файл |
| `createNote` | запертый родитель сносится так же, как архивный |
| `setReadOnly` | **единственная правка, которую запертая заметка переживает** — иначе замок был бы односторонним, то есть ловушкой |

Ради последней строки появился protected `rewriteNoteAllowed` — тот же
`rewriteNote` без вопроса о доступе, с одним вызывающим.

### 2.2 Ядро: виртуальные папки

```cpp
struct VirtualNote { QString id; QString title; QString path; };
struct VirtualFolder { QString id, title, icon; bool readOnly; std::vector<VirtualNote> notes; };
void addVirtualFolder(VirtualFolder);
const VirtualNote* virtualNoteAtPath(const QString& path) const;
static bool isVirtualId(const QString& id);   // id содержит ':'
```

Id виртуальной заметки — `info:README`. Двоеточия в настоящем id (14 знаков
base-32) не бывает, поэтому вопрос дёшев и однозначен. Путь — путь **ресурса**
(`:/docs/info/README.md`): его открывает `QFile`, значит `readFileBytes` и
`ZNote::load` работают без единой оговорки, и второго пути «из markdown в
документ» не заводится. Заголовок строки, если его не задали, хранилище
спрашивает у самого документа — как у настоящих заметок.

### 2.3 Документация — каталогом, а не списком

`docs/info/` теперь источник: `README.md` (копия корневого; корневой владелец
почистит отдельно до readme проекта) и `zametti-storage.md` (переезд целиком,
заголовок стал «Storage Organization»). CMake обходит каталог
(`file(GLOB … CONFIGURE_DEPENDS)`), порождает `info_docs.qrc` из шаблона
`app/info_docs.qrc.in`, `AUTORCC` его собирает. Пустой каталог — **ошибка
настройки**, а не пустая папка в окне.

`embeddedDocs()` перечисляет `:/docs/info/*.md` и возвращает пути. Таблицы
`kDocs` больше нет — ни в коде, ни в qrc: расширять документацию будут файлами.
Картинки рядом с документами поедут тем же обходом, и ссылки на них
разрешатся как `:/docs/info/<имя>` — картинный тракт читает через
`QFile`/`QFileInfo`, а те понимают `:/` наравне с диском.

`ZApp::addInfoFolder(storage)` заводит папку при открытии **всякого** хранилища,
включая пустое.

### 2.4 Окно

* `NoteTreeModel`: узлы `virtualFolder`/`virtualNote`, значок по имени
  (`iconName` — одно поле вместо трёх ветвей: архив и бюро находок переехали
  туда же), `appendVirtualFolders` зовут **все три** ветки `build()`, включая
  пустую; `notesInSubtree` отдаёт содержимое виртуальной папки и не пускает его
  в чужие списки; `flags()` снимает `ItemIsEditable`/`ItemIsDragEnabled` и не
  ставит `ItemIsDropEnabled` у запертого — этим F2, перетаскивание и приём
  умирают, не доходя до команд.
* `NoteListModel::setFixedOrder` — у виртуальной папки порядок задан списком.
* `ArchiveView` → **`ReaderView`** с тоном (`Tint::Aged` / `Tint::Plain`). Одна
  читалка на три рода: архивная заметка, запертая заметка, документация.
  Место чтения помнится по id — тем же хранилищем мест (`ZAppState`), что и
  каретки правимых заметок.
* `main.cpp`: страница `docView` в стеке, развилка у двери
  (`panels.noteChosen` → `showDoc` или `editor.openFile`), выход из режимов при
  входе в документ, уход документации при открытии заметки (одно место —
  `refreshReadingPages`, подписанное на `fileChanged`), масштаб и облик наравне
  с прочими видами, `refuseLocked` — одна формулировка отказа на все команды,
  контекстные меню без правящих пунктов на запертом, погашенные кнопки с
  объяснением.
* Окно без хранилища теперь держит **хранилище с пустым корнем**, а не
  `nullptr`: `isStore()` у него ложь, поведение прежнее, но виртуальные папки
  оно несёт — иначе документации не было бы ровно у того, кому она нужнее
  всех.

### 2.5 Окно «About»

`aboutMarkdown()` — имя, что это, copyright и GPL-3.0, строка «документация — в
папке Info», дальше целиком прежняя сводка сборки. Вкладок две. Корневой
README из ресурсов ушёл: его место занял `docs/info/README.md`.

## 3. Что нашлось по дороге

### 3.1 Второй ресурс молча оказался пустым

Порождённый `info_docs.qrc` дал свой символ инициализации, и в **статической**
библиотеке компоновщик выбросил его так же, как когда-то первый: программа
поднялась с пустой папкой Info и жалобой `no embedded docs`. Лечится вторым
`Q_INIT_RESOURCE(info_docs)` рядом с первым. Ловушка ровно та, о которой
предупреждает комментарий в `app/CMakeLists.txt`, — и я в неё всё равно попал.

### 3.2 Переключатель сортировки перекладывал документацию

`build()` зовёт `sortStore` ДО того, как виртуальные папки добавлены, — и всё
выглядело верно. А `setRootSort` пересортировывает **готовое** дерево, где они
уже на месте: README и «Storage Organization» молча менялись местами.
Поймал набор. Теперь `sortStore` в виртуальную папку не заходит вовсе, а её
ранг ставит ниже архива.

### 3.3 Заголовки документов стоили 40 мс на каждом открытии хранилища

Заголовок строки берётся из самого документа — и узнаётся он единственным
честным способом: документ разбирается и собирается (`ZNote::load`), второго
пути «из markdown в заголовок» в программе нет. На наших двух документах
(README и Storage Organization — 243 и 924 строки с таблицами и кодом) это
**20–40 мс в Debug**, и платились они при КАЖДОМ открытии хранилища, то есть
и на каждом переключении.

Документы при этом вшиты в бинарник и за время работы не меняются. Значит,
считать их заголовки больше одного раза незачем: `ZApp` собирает папку один раз
и дальше раздаёт готовую копию. Замерено, а не объявлено: набор печатает оба
числа и **требует**, чтобы второе было на порядок меньше первого: 39 756 мкс
против 2 в последнем прогоне.

### 3.4 Таблица появлялась только после щелчка — вёрстка Qt врёт на первой отрисовке

Нашёл владелец: «открываю Storage Organization — таблички не видно, вместо неё
пустое место; ткнёшь — появляется». Воспроизводится железно: любой щелчок по
документу или прокрутка показывают её сразу.

**Замер, а не догадка.** Временная проба в `NoteView::paintEvent` печатала, что
видно и с какого блока идёт обход наложения. На первой отрисовке документа:

```
проба: видимое 0..705, полоса=0, hitTest=4727, старт=блок 60 (верх 4130),
       блоков 397, высота вёрстки 34734
```

Спросили про ВЕРХ документа (`hitTest(0, 0)`) — вёрстка ответила позицией 4727,
то есть блоком 60, чей верх на 4130 пикселей ниже видимой полосы. Обход
наложения тут же обрывался (`rect.top() > visible.bottom()` → break), и не
рисовалось НИЧЕГО из того, что рисуем мы поверх текста: сетка таблиц, плашки
кода, черты-разделители, рамки объектов. Следующая отрисовка — после любого
события — отвечала уже верно (`hitTest=0, старт=блок 0`).

Сличение снимков одного и того же места до и после починки это подтверждает: до
неё нет ни черты под вводным абзацем, ни серой плашки блока кода — не только
таблицы.

**Почему на обычных заметках не видно.** Редактор после открытия сам трогает
раскладку (`revealInGolden(caretRectInDocument())` — показать каретку), и она
успевает достроиться до первой отрисовки. У страниц ЧТЕНИЯ каретки нет, трогать
раскладку некому — и врала она каждый раз. Тем же болели архивная заметка и
слепок истории, просто на них никто не смотрел так пристально.

**Починка — не заплатка, а недоверие.** `NoteView::blockAtHeight(top)`: спросить
вёрстку и ПРОВЕРИТЬ ответ — блок обязан накрывать высоту, а не лежать под ней;
лежит — поднимаемся к началу. В здоровом случае цикл не делает ни шага. Помощник
один на все три обхода: экран (`paintEvent`), бумага (вывоз PDF — он обязан
совпадать с экраном слово в слово) и подложка слепка истории.

Владелец предложил «однократно заворсить перерисовку после показа» — это
вылечило бы симптом на странице документации, но не на бумаге и не в истории, и
оставило бы в коде веру в чужой ответ. Заплатка не понадобилась.

**Приколото набором.** `InfoFolder` спрашивает вёрстку СРАЗУ после подмены
документа, до единого другого обращения к ней (любое достраивает раскладку и
ложь прячет), печатает её ответ — на нашем корпусе это «5052 → блок 63» — и
требует, чтобы `blockAtHeight(0)` вернул блок 0. Проверка умеет краснеть:
снял починку — покраснела, вернул — позеленела.

### 3.5 Ctrl+F искал не в том, что на виду

`searchTarget()` в окне перечислял режимы — настройки, исходник, история — и
падал в редактор. Страницы ЧТЕНИЯ в этом списке не было вовсе, а значит, поиск
по открытой документации шёл бы в спрятанный редактор: на экране не
происходило бы ничего.

Тем же дефектом жила и АРХИВНАЯ заметка — до этой сессии: показывал её
`archiveView`, а Ctrl+F искал в редакторе. Порядок в `searchTarget` теперь тот
же, что и в `showPage`, и это правило названо в комментарии: искомое — та же
страница, что на виду. Одна строка вылечила обе.

### 3.6 Буква на картинке гасила весь интерфейс навсегда

Нашёл владелец: выделить картинку курсором или щелчком, нажать любую букву — и
дерево, список, тулбар становятся серыми, в полосе сведений совет про подпись,
выйти нельзя иначе как закрыв программу. То же с таблицей и с выключной
формулой.

**Причина — не в буквах, а в проводах.** Совет уезжал сигналом `importStatus`, а
это сигнал ВВОЗА КАРТИНОК: пока его текст непуст, окно гасит дерево, список и
тулбар — «везём, менять заметку и уходить с неё нельзя». Ввоз в конце шлёт
пустую строку и отпирает. Совет не шлёт ничего — и окно оставалось запертым
навсегда. Один сигнал делал две работы, и вторая работа не знала про первую.

**Починка — разделить провода и убрать реакцию.**

* `NoteEditor::hint(text)` — новый сигнал: сказать и забыть. Полоса сведений
  показывает и сама гасит через три секунды; НИЧЕГО не запирается. Туда ушли все
  советы («у таблицы подписи нет», «у вики-вложения нет подписи»).
* `importStatus` остался ТОЛЬКО у ввоза, и в его комментарии теперь написано
  прямо: этот сигнал запирает окно, и всякий, кто в него пишет, обязан прислать
  следом пустую строку.
* **Буква на объекте не делает ничего и не говорит ничего** (решение владельца):
  нажатие проглочено, и на этом всё. Клавиши слоя объекта — Enter (править),
  Ctrl+Enter, Shift+Enter, стрелки, Del/Backspace, Ctrl+D — работают как
  работали; F11 (полный экран) принадлежит окну и не менялся.

**Приколото набором** `ObjectKeys`: матрица «три рода объектов × два состояния
каретки (на объекте и объект выделен) × восемь печатных клавиш». На каждом
нажатии спрашивается двое: документ цел И `importStatus` не приходил ни разу —
то есть окно не могло запереться. Плюс обратная сторона: Enter открывает правку,
Ctrl+D у таблицы и формулы отвечает ПОДСКАЗКОЙ. Проверка умеет краснеть: вернул
прежнюю проводку — покраснела на всех трёх родах, вернул починку — позеленела.

Два состояния каретки в матрице не для красоты: слой объекта считает выделение
«не своим делом» (`actionFor` отдаёт `None`, если есть выделение), и владелец
назвал оба случая — «выделяем курсором ИЛИ кликом».

### 3.7 Счёт отличий «m/n» в баннере истории

Просьба владельца: F4 ходит по отличиям слепка, и хорошо бы видеть, на котором
из скольких стоишь — надписью у ПРАВОГО края той же строки, где «Snapshot …».

Сделано: `HistoryBanner::setHunk(index, total)` — своя надпись, а не хвост
строки слепка. Это не мелочь: строка слепка ужимается многоточием в узком окне
(на снимке приёмки «узко» от неё осталось «Snapshot from .»), и счёт, будь он её
хвостом, исчезал бы первым — а он короткий и нужен всегда.

Список кусков считает сам вид разности тем же `hunkFrom`, которым ходит F4:
второго понятия «кусок» в программе нет, и разойтись счёту с ходьбой негде.
Обход всего документа — РОВНО ОДИН на показанную разность (список живёт до
следующей подмены документа), потому что F4 нажимают подряд, и платить длиной
заметки за каждый шаг незачем.

Обновляется одним местом на оба пути — сигналом `hunkChanged`, который вид шлёт
и при свежем показе разности, и на каждом шаге: дверей три (F4, Shift+F4, смена
слепка), а правило одно.

До первого шага показывается **«—/6»**, а не «0/6»: «ни на котором» — это не
«на нулевом». Скажи, если предпочтёшь ноль.

Приколото набором `HistoryView`: счёт спрашивается на каждом шаге вместе с самой
ходьбой (первый, второй, круг, шаг назад), и отдельно — что НАДПИСЬ В БАННЕРЕ
показывает то же самое. Проверка краснеет, если снять оповещение. Снимки
приёмки: `история-счёт-широко.png` и `история-счёт-узко.png`.

### 3.8 Баннер истории: слово «compare:» убрано в кнопки

Владелец увидел на готовом: `compare:` стояло вплотную к счёту отличий, и две
короткие надписи рядом читались как одна. Отдельного слова больше нет — глагол
переехал на сами кнопки: **`[diff vs previous]` `[diff vs current]`**. Между
счётом и первой кнопкой — воздух: счёт не подпись к ним.

Из двух названных владельцем вариантов взят короткий (`diff vs …`, а не
`compare w. …`): он говорит тем же словом, что и ходьба по отличиям, и не
требует сокращения с точкой.

### 3.9 Ctrl+− в истории уменьшал живую заметку

Нашёл владелец: «нажимая Ctrl+=/Ctrl+− в истории, вижу влияние и на зум в
основном окне — при выходе из истории текст стал меньше». И добавил: «такая
ошибка уже была раньше».

Была — у РЕЖИМА ИСХОДНИКА, 19.08.2026: «Ctrl+= в исходнике молча увеличивал
скрытый обычный вид: отжал `[M]`, а заметка вдруг крупнее». Тогда режиму дали
своё число (`plainZoom` в state.json). У истории его не дали — она осталась в
ветке «обычный вид», и комментарий рядом объяснял это как замысел («масштаб
один на программу»). Замысел устарел: разность читают иначе, чем заметку.

Починка:

* `ZAppState::historyZoom` — своё число у режима, переживает перезапуск. Нет
  ключа — берётся масштаб заметки, чтобы режим открылся тем же кеглем.
* **Развилка стала чистой функцией** — `app/zoom_target.h`, `zoomTargetFor`.

## 8. Продолжение 27.08.2026: тулбар не восстанавливался после документации

Владелец на следующее утро: **«после просмотра помощи toolbar не
восстанавливается, многие кнопки по-прежнему задизаблены»**, и правило: *«при
переключении на заметку нужно ВСЕГДА обновлять тулбар в зависимости от свойств
заметки (read-only и т.д.)»*.

Это не новая беда, а мой долг §6.4, названный вслух и оставленный на потом. Так
делать нельзя, и владелец сказал почему: **«я такие вещи иногда пропускаю, а это
не долг, это ошибка, которая мешает пользоваться программой»**. Долг закрыт в
тот же заход.

### 8.1 Причина: правило лежало ниже своих поводов

Доступность кнопок считала лямбда `refreshToolbar` в `main.cpp`, и звали её
ровно четыре раза: из показа документации и трижды из смены хранилища. **При
смене заметки — ни разу.** Открыл документ → кнопки погасли; вернулся к
заметке → страница сменилась, а кнопки остались серыми с подсказкой
«documentation is read-only».

Позвать пересчёт из места, где заметка сменяется, было **физически нельзя**:
`refreshReadingPages` объявлена на 1125, `refreshToolbar` — на 2343, и лямбда не
видит объявленную позже. То есть это не забывчивость, а дефект расположения:
всякая новая дверь, открытая выше, обречена была забыть тулбар.

Та же дыра работала и на настоящих заметках: переход с запертой или архивной на
обычную кнопки тоже не пересчитывал — их состояние отражало не заметку, а
момент последнего из четырёх вызовов.

### 8.2 Починка: правило — функцией, проводка — объектом

* **`app/toolbar_state.h`** — чистая функция `toolbarPromiseFor(кнопка,
  состояние) → почему нельзя`. Плоский набор признаков, ни одной ссылки на живые
  объекты: правило проверяется перебором, без единого виджета. Тем же приёмом
  живут `actionFor` (слой объектов) и `zoomTargetFor` (масштаб) — третий случай
  за две сессии, и это уже не совпадение, а работающий приём.
* **`app/toolbar_controller.{h,cpp}`** — проводка. Контроллер САМ подписан на
  смену заметки (`NoteEditor::fileChanged`) и на смену показанного документа
  (новый сигнал `ReaderView::shownChanged`). Подписка внутри объекта — значит её
  видно набору; забытая подписка и была бедой.
* Заводится он в окне **после** подписки страниц чтения, и это не вкус: сигналы
  доставляются в порядке подписки, и пересчёт, вставший раньше, считал бы кнопки
  по ЕЩЁ НЕ УБРАННОЙ документации.
* Режимы (история, исходник, настройки) зовут `refresh()` сами: режим поверх
  документации закрывает её собой, и запрет с экрана обязан уйти вместе с ней.
* `refreshToolbar` в окне остался тонким и делает только то, что принадлежит
  ОКНУ: сообщение «No storage open …» в полосе сведений.

### 8.3 Ловушка, вскрытая по дороге: подсказки кнопок

`setPromise(id, "")` собирал подпись кнопки заново из таблицы — и **затирал
живую**. Пока пересчёт случался четырежды за запуск, этого никто не видел; с
пересчётом на каждую смену заметки кнопки сортировки теряли бы подпись про
НАПРАВЛЕНИЕ ежеминутно, а кнопка панелей писала бы «Hide side panels», показывая
панели. Теперь тулбар помнит подпись (`tips_`), а собирает её из подписи,
шортката и причины одним местом (`applyTip`). Кнопка панелей переведена с прямой
записи в тултип на `setTip` — иначе тулбар про неё не знал.

Заодно появился `Toolbar::promiseFor` — прежде обещания писались и никем не
читались, и набору доставалась только погашенность, без причины.

### 8.4 Чем проверено

* **Набор `ToolbarState`, два слоя.** Первый — правило перебором: для каждого
  состояния мира названы ВСЕ погашенные кнопки, и всё прочее обязано гореть
  (завели новую кнопку — набор скажет, что про неё не подумали). Второй —
  живой стенд с `Toolbar`, `NoteEditor`, `ReaderView` и контроллером, где
  **`refresh()` руками не зовётся ни разу**: всё состояние обязано приезжать
  сигналами. Там же — симметрия «переключился-вернулся == открыл заново»,
  инвариант «нажатость не сбивается» и «живая подпись переживает пересчёт».
  Снял любую из двух подписок — краснеет.
* `open_storage_test` больше не воспроизводит правило руками, а спрашивает
  настоящее: своя копия правила проверяла сама себя.
* **Живьём** под Xvfb, случай владельца дословно: Info → README → обратно на
  заметку, три снимка тулбара и чернила по кнопкам —

  | состояние | ввоз картинок | история | `[M]` |
  |---|---|---|---|
  | обычная заметка | 159 | 115 | 143 |
  | на документации | 0 | 0 | 0 |
  | вернулись к заметке | 159 | 115 | 143 |

  То есть тулбар восстанавливается точь-в-точь.
