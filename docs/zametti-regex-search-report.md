# Отчёт: регулярные выражения в поиске и замене, режим экрана в поиске по базе

Ветка `regex-search`, 27 августа 2026, четырнадцать коммитов. Продолжение того же
дня: утром — давний красный `FuzzOps` (`zametti-regex-search` не трогает его,
провалов там как было 11, так и осталось).

## 1. Итог

* поиск и замена умеют регулярные выражения — тумблером в панели;
* поиск по хранилищу ПОВТОРЯЕТ РЕЖИМ ЭКРАНА: обычный вид ищет по тексту, `[M]`
  по markdown (из-за этого `# vector` раньше находился в одной заметке и не
  находился по базе);
* поиск на большой заметке перестал вставать колом: **4029 мс → 2 мс** на первую
  тысячу вхождений «`.`» по заметке в 8.4 МБ;
* наборы: Release 132 из 133, Debug столько же; красный один и прежний.

## 2. Сперва один перечислитель, потом выражения

«Пройти по вхождениям» было написано ТРИЖДЫ и по-разному: `ZDocument::find`,
`NoteSearch::find` и `ZDocument::replaceAll` (там вообще `QTextDocument::find`).
Прикрутить выражения к трём обходам значило бы завести три места, где правила
разойдутся, — а они и так расходились: **счётчик считал перекрывающиеся
вхождения, а «заменить всё» их не считало**, и на «ааа» панель показывала «2
найдено», меняя одно.

Поэтому первым делом появился общий `forEachHit` (`doc/search.cpp`), и все трое
живут поверх него. Там же, ровно по одному разу, записаны правила про объекты
(ищем по исходнику), про границу объекта, про шаг и про пустое совпадение.

Запрос тоже один: `Query` получил признак `regex`, само разобранное выражение и
`valid`, а `TextSearchTarget::findMatches` берёт `Query` целиком вместо россыпи
из букв и регистра.

## 3. Решения владельца, вшитые в правила

| решение | что из этого следует |
|---|---|
| перекрывающихся вхождений нет: «аа» в «ааа» — одно | шаг через длину найденного; счётчик и замена наконец считают одинаково |
| пустая ГРУППА законна (как в perl), пустое СОВПАДЕНИЕ целиком — не находка | «(\d+)?текст» находит, `$1` пуст; «а*» на «бббаа» находит «аа», а не пять пустот |
| `^` и `$` — края физической строки | перенос по ширине окна дело показа; мягкий перенос (U+2028) приводится к «\n» |
| `[.\n]+` и подобное обязано работать | подлежащее — весь блок, и многострочный кусок кода находится |
| недописанное выражение — красные БУКВЫ и ни слова об ошибке | правка продолжается, счётчик молчит, в историю такое не кладётся |
| `$n` или `\n` в замене — годится любое | сделаны обе записи, плюс `$0`, `${12}`, `\U \L \u \l \E` |
| потолок в тысячу совпадений | «1000+/?», пока никуда не встали, и «5/1000+», когда встали |
| стрелки обхода — значками `arrow-up`/`arrow-down` | все четыре кнопки панели говорят языком тулбара; три настройки-глифа сняты |

## 4. Четыре замера, которые изменили код

**1. U+2028 для PCRE2 — обычный знак.** «^» на нём не срабатывает, «.» его ест,
«\s» его не видит. Мягкий перенос (Shift+Enter) — настоящая строка (в файл
уходит переводом), поэтому текст для поиска приводится: U+2028 → «\n», знак в
знак, смещения не съезжают.

**2. Без `UseUnicodePropertiesOption` «\w» и «\b» — только про ASCII.** «\w+» не
находит НИ ОДНОГО русского слова, «\bкот\b» — ни одного кота. Для заметочника на
русском это не мелочь, а негодность; опция включена всегда.

**3. `match(text, from)` в цикле квадратичен.** На заметке в 8.4 МБ:

```
match(from) в цикле, первая тысяча вхождений «.»   4029 мс
globalMatch,          первая тысяча                   2 мс
globalMatch,          все 8 179 347 вхождений       626 мс
```

Каждый вызов платит за весь текст заново. По ЗАМЕТКЕ это пряталось (подлежащее —
блок, куски мелкие: стенд показывал 673 мкс), а по ПЛОСКОМУ тексту — вид
исходника и поиск по базе в `[M]` — вставало колом на первой же букве.

**4. `toPlainText()` 8.4 МБ = 15 мс**, и вид исходника платил это на КАЖДУЮ
букву запроса, хотя документ между буквами не менялся. Теперь плоский текст
живёт при виде и освежается по ревизии документа.

Итого набор буквы в поле поиска на большой заметке: секунды → ~2 мс.

## 5. Поиск по базе повторяет режим экрана

Раньше `Ctrl+Shift+F` вёл себя не как `Ctrl+F`: по базе и по открытой заметке в
обычном виде ищет один путь (текст блоков, без разметки), а `[M]` — совсем
другой (плоский markdown). Теперь режим экрана задаёт смысл: в `[M]` ищем по
`liveMarkdown()` (по тому же тексту, который показывает вид, а не по байтам
файла — файл может быть не в каноне). Щелчок по такой находке ОТКРЫВАЕТ `[M]` и
прыгает туда же; находка в тексте, наоборот, из `[M]` выводит.

## 6. Мои ошибки

1. **Написал `\u` поверх `\L` не как в perl** — одно состояние регистра вместо
   двух, и «\L\uслово» давало «слово» вместо «Слово». Поймал набор, который я
   писал по перловой семантике; починил код, а не ожидание.
2. **Написал обход выражением так, что он квадратичен** — `match(text, from)` в
   цикле. Нашлось только потому, что владелец попросил про отзывчивость и я сел
   мерить; сам бы не пошёл — по заметке-то было быстро.
3. **`git add -A` увёз набор в коммит починки**, хотя в сообщении было написано
   «переписан следующим коммитом». Заметил на `git show`, коммит разобрал и
   собрал заново.
4. **Дважды промахнулся с ожиданием в наборе**: «# vector» находится и внутри
   «## vector types» (та же подстрока), и полторы тысячи совпадений теперь
   упираются в потолок. Оба раза правил ожидание, а не код, — но проверял, что
   правило и вправду сменилось, а не что «так вышло».
5. **Обрезал README про иконки** неаккуратной правкой и восстановил из git.

## 7. Что осталось

* **Замены по хранилищу нет** (решение владельца: пока нет). `replaceAll` умеет
  открытая заметка в обоих видах.
* **`FuzzOps` — те же 11 углов md4c**, эта работа их не касалась.
* Подсветка найденного считается по видимому окну и при прокрутке
  перекладывается — это уже O(показанного); кэшировать её нечем, она зависит от
  прокрутки, а не от текста.
