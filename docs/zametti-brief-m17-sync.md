# Zametti — бриф №17 (предварительный): облачная синхронизация

Статус: **финальный** — все решения утверждены владельцем (дизайн-сессии
docs/etaps + сессия ответов 22.08).

## Контекст

Хранилище: плоские `<id>.md` + вложения `<id>.<ext>` + `history/<id>.log`
(CBOR, zstd-поколения по 32, опорная запись, tombstone, truncate со
сторожами). Времена — ISO-8601 с офсетом, сравнения по UTC (этап 15). Архив:
стаб + тело в журнале, запись стаба — запись журнала (голова ≡ файлу и для
архивных). BLAKE3 — проектный хеш, считается в пути сохранения.

**Центральное решение владельца: облако хранит ТОЛЬКО журналы + вложения +
keyfile.** `.md` — локальная материализация головы журнала; иерархия и
сортировки едут в журналах папок; ничто не хранится дважды.

Обязательное чтение: zametti-storage.md; отчёты 7, 10, 15; CLAUDE.md.

## Цель этапа

1. Крипто-слой: мастер-ключ, keyfile, шифрование блобов.
2. Адаптер удалённого хранилища (5 операций) + реализация WebDAV.
3. Синк-движок: выравнивание → обмен → объединение → материализация.
4. UI: кнопка облака оживает (статус, прогресс, отмена), секция конфига.
5. `zametti-store sync` — тот же движок из CLI (тесты и скрипты).

## Не-цели

- S3 — вторым заходом (адаптер обязан его допускать; SigV4 не здесь);
- синхронизация config.json (припарковано владельцем до стабилизации
  настроек), state.json, sync-state, rescue — локальные по определению;
- селективный синк, мультипользовательские права, конфликт-UI (его нет по
  построению: union + голова), тома журналов (план Б, формат готов);
- синк config.json — припарковано; Windows-keyring (DPAPI) — при
  Windows-порте; периодический автосинк включён кодом, но дефолт «вручную».

## Часть 1: крипто

- **Конверт ключей**: мастер-ключ 32 байта случайный; keyfile на сервере =
  ключ, завёрнутый через Argon2id(пароль) + AEAD; смена пароля = перезаворот
  keyfile; ротация ключа = новый ключ + полная перезаливка (штатная, минуты);
- **блоб**: plaintext (журнал как есть — zstd уже внутри; вложение как есть —
  JXL уже сжат) → XChaCha20-Poly1305 целиком, случайный 24-байтовый nonce на
  каждую заливку, nonce+тег в обёртке блоба с версией формата; **версия
  формата, тип блоба, storeId и имя блоба идут в associated data (AAD)** —
  защита от downgrade обёртки и подмены/путаницы блобов, стоит ноль;
- имена на сервере — открытые id (решение владельца: id непрозрачны, плоско);
- **крипто-вендор: libsodium** (решение владельца), на данном этапе БЕЗ
  вендоринга — системная зависимость (find_package/pkg-config; в Ubuntu и
  brew повсеместен; configure печатает «собирается / НЕ СОБИРАЕТСЯ +
  причина», как для Qt). Android-порт вернётся к вопросу вендоринга, когда
  наступит. До кода: тест-векторы XChaCha20-Poly1305 и Argon2id из RFC,
  калибровка параметров Argon2id на его машине (целевое время ~0.5–1 с,
  параметры — в keyfile рядом с солью, чтобы будущие устройства читали их
  оттуда, а не из констант).

## Часть 1б: идентичность хранилища

- **store-id** чеканится при первой настройке синка тем же генератором
  14-символьных id, что заметки; живёт в **видимом `zametti.json` в корне
  хранилища** `{storeId, formatVersion, created}` — идентичность путешествует
  вместе с данными (копия каталога знает, чьё облако её). Абзац в
  zametti-storage.md обязателен; загрузчик заметок не-`.md` файлы игнорирует;
- **zametti.json — сам объект синхронизации**: его облачная копия — манифест
  (открытым текстом сознательно — сверка работает ДО ввода пароля; утечка
  нулевая, id непрозрачен). Семантика слияния для него УНИКАЛЬНА: не union,
  а **равенство** — расхождение storeId = ошибка адресации → честная
  остановка «это облако принадлежит другому хранилищу». Страж от
  union-слияния двух несвязанных баз по опечатке в remoteDir;
- **formatVersion** — страж совместимости: клиент, увидевший формат новее
  своего, вежливо отказывается до каких-либо действий («обнови программу»);
- второе устройство id не чеканит, а **наследует**: бутстрап пишет локальный
  zametti.json из манифеста;
- **sync-state** (бухгалтерия) — кэш пер-девайсный: живёт в локальном
  каталоге приложения (рядом со state.json), файл именуется по storeId
  (несколько хранилищ — несколько файлов без коллизий); с копией каталога
  хранилища НЕ путешествует;
- дефолтный `remoteDir` включает store-id; человеческое имя (mynotes) —
  локальный ярлык, уникальности не требует;
- **форк копией каталога — задокументированное минное поле**: `cp -r` +
  независимые правки двух копий с одним storeId = одно облако и молчаливый
  union двух разошедшихся баз (страж по storeId тут не срабатывает — id
  совпадает). Лечение: команда **«отвязать» (fork)** — перечеканка storeId
  для копии; абзац в zametti-storage.md; sync-state именуется по
  (storeId + хеш локального пути), чтобы две копии на одной машине не
  делили бухгалтерию.

## Часть 2: адаптер

```
list()                → [{имя, размер, etag}]
get(имя)              → байты
put(имя, байты)       → etag        (+ вариант с if-match, опционально)
del(имя)
mkdirOnce()           — только WebDAV, один раз
```

- **WebDAV**: PROPFIND Depth:1, PUT/GET/DELETE, basic auth поверх TLS;
  If-Match — использовать, если сервер честен, деградировать молча;
- нестабильные etag (болячка WebDAV) переживаются ярусом хешей — etag только
  подсказка;
- тесты — контейнер wsgidav; каркас адаптера обязан позволить S3-реализацию
  без правки движка (это проверяется вторым, фиктивным адаптером в тестах —
  локальный каталог как «сервер»; он же ускоряет все тесты движка).

## Часть 3: движок. Порядок шагов — инвариант

`выравнивание → обмен → объединение → материализация` — всегда в этом
порядке, каждый прогон, без исключений.

**Режимы прогона (решение владельца).** Их два:

- **Полный** — кнопка и старт программы. На старте — в фоне, с акцентом на
  входящие: программа открывается сразу, прилетевшее материализуется по
  ходу (открытая заметка — через external-путь). Исходящее на старте обычно
  вырождено: выход предыдущей сессии уже всё отдал.
- **Push-only при выходе** — только исходящее: выравнивание + заливка
  блобов, чей удалённый etag совпадает с записанным (fast-forward push).
  Блобы, требующие слияния (сервер тоже менялся), пропускаются и достаются
  следующему полному прогону — union гарантирует, что отложенное не
  теряется. Выход ограничен по времени ПО ПОСТРОЕНИЮ: ни скачиваний, ни
  слияний, ни материализации. Бюджет: `sync.exitPushBudgetSec` (дефолт 10) —
  заливка режется по бюджету, остаток достаётся следующему прогону без
  потерь (с ранней заливкой вложений выход обычно = журналы, килобайты).
  Офлайн при выходе → тихий пропуск, dirty-set персистентен, следующий
  прогон доделает.

### Время и порядок (пакет двух аудитов)

**Инвариант: слияние — чистая функция от набора записей.** Ничто в логике
слияния не зависит от «текущего момента» — иначе разные now двух устройств
дают разный порядок и убивают сходимость. Всё живёт в самих записях.
Разделение: ISO-8601 с офсетом — поле для людей; порядок — по ключу ниже.

- **Слой A, монотонный страж (локальный)**: время новой записи
  `t = max(now_utc, last_written + 1мс)`; `last_written` — персистентно
  рядом с sync-state, в облако не едет. Самоинверсия своих записей
  (dual-boot RTC, скачок NTP, ручная переводка) исключена по построению;
  потеря last_written → деградация к wall clock без поломки.
- **Слой B, Lamport-счётчик**: в заголовок записи — поле `seq` (varint);
  при записи `seq = max(seq всех известных записей заметки) + 1`.
  **Порядок и голова: max(seq, time, fingerprint)**; ключ идентичности
  union НЕ меняется — (time, fingerprint). Каузально-поздняя правка бьёт
  «запись из будущего» независимо от часов: отравленная голова живёт до
  первой правки, не сутки. Миграция: старые записи seq=0 (между собой — по
  времени, как раньше), первая новая правка законно становится головой.
- **Тайбрейк при полностью равном ключе: контент старше tombstone** —
  edit-wins детерминированно, отпечаток не решает судьбу заметки.
- **Слой D, диагностика без блокировок**: входящие записи с t > now + W →
  статус «устройство сообщает время из будущего — проверьте часы»; локально
  now < last_written − W при старте → статус «часы переведены назад». Не
  диалоги, работу не останавливают.
- Слой C ревьюера (окно |Δt| > W в тайбрейке) **отклонён**: компаратор
  нетранзитивен → нет тотального порядка → недетерминизм сортировки. Если
  эффект когда-нибудь понадобится — тотальная форма через floor(t/W).

### Шаг 1: выравнивание — O(изменений), не O(хранилища)

Принцип (решение владельца): «голова ≡ файлу» поддерживается ТРАНЗАКЦИОННО
единственным путём записи (файл + запись журнала — одна операция), поэтому
сплошная перепроверка инварианта на каждом синке — двойная бухгалтерия.
Заметка, которую не трогали, не стоит синку НИЧЕГО. Три яруса обнаружения:

1. **Dirty-set** (основной механизм): хранимое множество id, тронутых с
   последнего синка; пометка — write-ahead, ДО записи (упали посреди
   сохранения → заметка в множестве → проверится одна). Каждое
   сохранение/запись журнала добавляет id; синк обрабатывает только это
   множество. По каждому id из него: BLAKE3 файла против головы; разошлись →
   дописать запись (external/save семантика); журнала нет → родить с опорной
   записью (время из файла).
2. **Stat-скан** (десктоп, по умолчанию включён): один readdir со сравнением
   (mtime, размер) `.md`-файлов против записанных в бухгалтерии — ловит
   правки vim-ом при закрытой программе. Метаданные каталога, ноль чтений
   содержимого. Расхождение подсказки → BLAKE3 этого файла → как выше.
   **Мобильные платформы (песочница, внешних писателей нет): скан выключен
   по построению, работает чистый dirty-set.**
3. **Полный BLAKE3-проход** — только ручная команда `verify --deep`
   (включая decode-пробу вложений, см. шаг 3).

Лестница деградации честная: dirty-set потерян → stat-скан находит всё,
что находимо статами; поправка доктрины (решение владельца): быстрая
проверка (mtime, размер) принята полом корректности — класс rsync/Syncthing;
сфабрикованная правка с восстановленным mtime ловится только verify --deep.

Первый синк: dirty-set пуст, но журнала нет у ~129 заметок → они все
проходят выравнивание и дожурнализуются опорными записями — главная работа
первого прогона, секунды. Архивные стабы выровнены по построению.

Перешифровка при заливке касается ТОЛЬКО реально изменившихся журналов —
нетронутая заметка не стоит ни хеша, ни шифрования, ни байта трафика.

### Шаг 2: обмен — три яруса

Бухгалтерия `sync-state` (в локальном каталоге приложения, файл по storeId —
см. часть 1б; **кэш, не истина**): на блоб — etag
последней операции, BLAKE3 залитого шифротекста, BLAKE3 локального журнала
на тот момент.

1. etag сервера == записанный И локальный журнал == записанный → **пропуск**,
   ноль трафика;
2. etag разошёлся → GET → хеш шифротекста == записанный → перевыдача etag,
   обновить бухгалтерию, пропуск; иначе — настоящее изменение;
3. менялась одна сторона → **принять/залить целиком без слияния** (наш
   журнал == последнее сошедшееся, чужой — его union-расширение);
4. менялись обе → полное слияние (шаг 3).

Потеря sync-state → всё честно деградирует в «скачать и слить», идемпотентно.

**Целостность журнала — прежде классификации.** Прежде чем счесть локальный
журнал «изменившимся», он проходит валидацию: CBOR-обход + отпечатки записей
(рваный хвост после штатной подрезки — валиден; настоящая порча отпечатки не
проходит). Не прошёл → трактуется как **absence** (absence-agnostic
философия): принять удалённый целиком, **ноль заливок** — локальный бит-рот
никогда не уезжает в облако. Симметрично: **журнальный блоб пропал на
сервере при записанном etag** = повреждение сервера → перезаливка-лечение
(в exit-push — откладывается до полного прогона).

### Шаг 3: объединение

- **union записей по ключу (UTC-время, отпечаток)** — никогда по времени
  одному (легальны записи в одну миллисекунду с разных устройств);
  absence-agnostic: слияние не спрашивает, почему записей нет (порча /
  подрезка хвоста — одно лечение);
- порядок и голова — **max(seq, time, fingerprint)** (см. «Время и порядок»);
- **прореживание журналов ОТКЛЮЧЕНО полностью** (решение владельца:
  вернёмся позже; журналы grow-only — при текущих масштабах незаметно
  годами; watermark-механизм и тома — план Б). Пересборка поколений при
  слиянии — та же машинерия, без правил прореживания. Truncate-примитив
  («набрали и отменили») жив; дубли, успевшие уехать на другое устройство
  до усечения, вернутся union-ом — принятая цена;
- **идентичность журнала = хеш канонического набора записей** (сортированные
  отпечатки), НЕ байты файла: «результат ≠ приехавшему» сравнивает наборы;
  наборы равны → **не заливать** (анти-ping-pong: zstd-байты вправе
  различаться между сборками, семантика — нет). Наборы различаются → залить
  слитое (сервер лечится, копии сходятся). Property-тест:
  merge(A,B) ≡ merge(B,A) побайтово при равных наборах;
- **вложения** (у них нет журналов; версия живёт В ФАЙЛЕ — идентичность
  путешествует с данными):
  - **встроенный XMP**: `Zametti:Rev` (Lamport-счётчик, рождается =1 при
    импорте) + `Zametti:Deleted` (флаг). JXL box / WebP chunk / JPEG APP1 —
    машинерия сохранения метаданных при импорте уже есть;
  - **ранняя фоновая заливка** (решение владельца): картинки шифруются и
    летят в облако СРАЗУ при въезде в хранилище, фоновым потоком импорта;
    статус-бар: «картинки: m/n зашифровано и залито». Журналы заметок —
    строго на батч-ритме старт/выход/кнопка (облако не спамится);
  - presence-синк по бухгалтерии (нет там → залить, нет тут → скачать);
    локальные изменения — подсказкой (размер, mtime) с хеш-подстраховкой;
  - **конфликт байтов под одним id — правило rev**: больший `Zametti:Rev`
    побеждает, молча (замена/пересжатие/ретушь = rev+1 → детерминизм без
    часов и вопросов). Автоматически разрешается и случай «одна сторона ==
    записанному хешу» (вторая просто новее). **Лестница целостности**
    (AEAD-тег → BLAKE3 против бухгалтерии → decode-проба) фильтрует порчу:
    нездоровая сторона проигрывает автоматически — лечение, не конфликт.
    Только **равный rev + разные байты** (истинно конкурентная правка) →
    элемент в **одном сводном диалоге на прогон** (никогда по диалогу на
    картинку): размеры/габариты, дефолт = больший файл, выбор по-элементно;
    решение фиксируется (пара хешей → победитель), та же пара не
    переспрашивается; после разрешения обе стороны сходятся к победителю;
  - **удаление** = замена на **мини-превью** (даунскейл по правилу площади,
    `maxDeletedImageSize`, дефолт S=100 → ≤10 000 px) + `Deleted` + rev+1;
    едет обычной заменой; заметки и снимки истории показывают рамку
    «удалено» с призраком-превью;
  - операции этапа — CLI-минимум `zametti-store attach replace|recompress|
    delete <id>` (ретушь-UI позже);
- **keyfile — правило когерентности** (бухгалтерия может быть потеряна,
  инвариант D): истина = «ключ из keyring расшифровывает актуальные блобы»;
  keyfile-чек по etag из листинга — дешёвый ранний сигнал. **Массовый
  AEAD-отказ входящих = ротация с другого устройства** → честная остановка
  и запрос пароля (не трактовать как порчу); UI различает «неверный пароль»
  (отказ разворота keyfile) и «ключ ротирован» (keyfile развернулся, блобы
  не читаются старым ключом).

### Шаг 4: материализация

- голова журнала → `.md` **штатной атомарной записью с самопроверкой**; хеш
  из записи сверяет распакованные байты;
- **условна вдвойне**: (а) голова ≠ файлу; (б) файл не менялся с шага 1
  (повторный BLAKE3) — менялся → повторное выравнивание этой заметки, не
  перезапись. Правился во время синка — не проигрываешь никогда;
- **открытая заметка** — через существующий external-путь: прилетевшее
  состояние применяется undoable-правкой, буфер не перетирается, Ctrl+Z
  возвращает твоё;
- tombstone-голова → файла нет (удалить локальный, если был; вложения — по
  каскаду архива/удаления, как локально);
- **предохранитель массового удаления** (решение владельца): материализация,
  желающая удалить > N заметок за прогон (конфиг, дефолт ~20) →
  остановка с показом списка. **Семантика отказа**: пользователь отклонил →
  эти заметки объявлены живыми → их файлы порождают записи ПОВЕРХ
  tombstone (штатный edit-vs-delete: правка побеждает) → облако лечится,
  вопрос не повторяется, потому что состояние изменилось. Один из двух
  вопросов во всём синке (второй — сводный диалог вложений).

### Первый вход нового устройства

Пустое хранилище + URL + пароль → скачать всё → расшифровать →
материализовать головы. Бутстрап = обычный синк с пустой локальной стороной;
отдельного кода восстановления не существует.

## Часть 4: UI и конфиг

- кнопка облака (обещание этапа 9) оживает: клик = синк сейчас; статус на
  кнопке (чисто / идёт с прогрессом / ошибка с текстом в тултипе); отмена —
  повторным кликом, прерывание безопасно в любой точке (порядок шагов +
  атомарность записей это гарантируют — тест); **ранняя заливка вложений**
  показывается в статус-баре: «картинки: m/n зашифровано и залито»;
- **когда синкать** (решение владельца): `sync.onStart` (дефолт вкл) —
  полный синк в фоне при старте, акцент на входящие; `sync.onExit`
  (дефолт вкл) — push-only исходящих при выходе, если были правки;
  кнопка — полный прогон в любой момент; `sync.intervalMinutes`
  (дефолт 0 = выключено) — периодический полный, на будущее;
- конфиг открыто: `sync.url`, `sync.user`, `sync.remoteDir` (не секреты,
  правятся руками как всё). **Секреты — в системном keyring, два пароля —
  две судьбы**:
  - *пароль WebDAV-сервера* → keyring (`zametti-webdav-<storeId>`);
    переспрашивается только по 401 или при утраченном keyring;
  - *пароль шифрования* **не хранится нигде и никогда**: живёт одно
    мгновение — Argon2id разворачивает/создаёт мастер-ключ, и в keyring
    ложится **ключ** (`zametti-key-<storeId>`), пароль стирается из памяти.
    Нужен ровно в четырёх случаях: настройка/новое устройство; ротация
    ключа; смена пароля (перезаворот keyfile); утраченный keyring.
  Механика: **mac** — Security.framework (SecItemAdd/CopyMatching, тонкая
  обёртка); **Linux** — Secret Service API прямо по QDBus (freedesktop-
  стандарт, GNOME Keyring и KWallet оба реализуют; НОЛЬ новых зависимостей);
  keyring недоступен (редкий WM) → деградация: запрос пароля при первом
  синке сессии, ключ в памяти процесса до выхода.
- **iCloud Keychain** (решение владельца): на Apple-платформах в диалоге
  настройки — галочка «синхронизировать ключ через iCloud Keychain»
  (kSecAttrSynchronizable), **дефолт ВЫКЛЮЧЕНО**, включение — осознанное
  дело пользователя; будущий iOS-порт («мало ли») унаследует бесплатно.
  Задача этапа: ad-hoc подпись с постоянным идентификатором и **ручная
  проверка на паре маков**, что второй мак читает элемент без капризов —
  галочка должна быть проверенной, не декоративной;
- **диалог первичной настройки** (единственный, один раз за жизнь
  устройства; это ввод данных, не подтверждение — принципу «никаких
  диалогов» не противоречит): url, логин+пароль сервера, remoteDir
  (предзаполнен store-id), пароль шифрования (дважды при создании; один раз
  на втором устройстве — после скачивания манифеста и keyfile). Дальше —
  ноль вводов в устойчивом режиме: оба секрета молча берутся из keyring;
- офлайн/нет сети → тихий статус «недоступно», никаких диалогов.

## Первая задача: разведка и замеры

1. libsodium: линковка системного, RFC-тест-векторы XChaCha/Argon2id,
   калибровка Argon2id на машине владельца (параметры → в keyfile).
2. Keyring-пробы: Secret Service по QDBus (записать/прочитать/удалить под
   GNOME Keyring), заготовка Security.framework для мака.
3. Контейнеры wsgidav + MinIO в тестовой обвязке (второй — на будущее S3,

4. Полный первый синк копии хранилища владельца (282 заметки, ~500 МБ

## Инварианты и тесты

```
A. Порядок шагов ненарушим; материализация никогда не раньше выравнивания
B. Слияние не теряет записей: union(A,B) ⊇ A и ⊇ B (property-тест на
   случайных журналах)
C. Файл не перетирается, пока его содержимое не в журнале (сценарий
   владельца: правка vim-ом при закрытой программе → синк → правка в
   таймлайне, ничего не потеряно)
D. Удаление sync-state не меняет результата синка (кэш, не истина)
E. Прерывание в любой точке безопасно: повторный прогон достраивает
F. Nonce никогда не повторяется (тест уникальности на прогоне);
   plaintext-подстроки в шифротексте отсутствуют
```

- первый синк: 282/282 журнализованы, облако = журналы+вложения+keyfile,
  ни одного `.md`;
- бутстрап: пустой каталог + пароль → побайтовое равенство материализованного
  хранилища оригиналу (кроме sync-state);
- двухдевайсная сходимость (fuzz): случайные правки/удаления/архивации на
  двух копиях → два раунда синка → хранилища идентичны, записи не потеряны;
- три яруса: пропуск без сети (mtime-проверка сервера), перевыдача etag
  (симуляция), принятие целиком, полное слияние; A,B,C,D против A,E,F,G,H
  (его сценарий) → union;
- обрыв заливки на половине (kill контейнера) → повторный синк лечит;
  порча блоба на сервере → AEAD-отказ → перезаливка своим (лечение);
- зоны: правки в +08:00, синк и сортировка в +03:00 — порядок верен;
- tombstone едет; массовое удаление → предохранитель; edit-vs-delete →
  правка побеждает;
- открытая заметка получает чужую версию undoable-правкой, Ctrl+Z жив;
- смена пароля; ротация ключа; чужой keyfile → честная остановка;
- **O(изменений) счётчиками**: устойчивый синк = 1 листинг (манифест и
  keyfile сверяются по etag ИЗ ТОГО ЖЕ листинга, GET — только при
  расхождении), 0 чтений содержимого заметок, 0 шифрований
  (инструментованный фиктивный адаптер); правка одной заметки → обработана
  ровно она; vim-правка при закрытой программе → stat-скан находит;
  mobile-профиль (скан выключен) → dirty-set достаточен; после нештатного
  завершения — разовый stat-скан на ЛЮБОЙ платформе (закрывает окно
  write-ahead-пометки без fsync; stat-скан также ловит УДАЛЕНИЯ — diff
  множества readdir против бухгалтерии; пропавший файл при живой голове
  журнала возвращается материализацией);
- **идентичность**: чужой remoteDir (несовпадающий storeId манифеста) →
  остановка до каких-либо записей; манифест с formatVersion новее → вежливый
  отказ; бутстрап наследует id из манифеста; форк: «отвязать» перечеканивает
  storeId, две копии на одной машине не делят sync-state;
- **параллелизм**: GUI + `zametti-store sync` одновременно → второй вежливо
  отказан по store.lock, sync-state цел; конкурентный двухдевайсный fuzz
  (синки внахлёст, не по очереди) → сходимость за ≤3 раундов, без потерь;
- **целостность журналов**: flip байта в локальном .log → валидация не
  прошла → удалённый побеждает, НОЛЬ заливок; журнальный блоб удалён с
  сервера → перезаливка-лечение (на exit-push — отложено);
- **детерминизм**: merge(A,B) ≡ merge(B,A) побайтово; равные наборы записей
  при разных zstd-байтах → ноль заливок (анти-ping-pong);
- **часы**: −3ч (dual-boot) → свои записи не инвертируются (страж A);
  +24ч соло → синк → чужая правка → отравленная голова сменяется сразу
  (seq); +24ч конкурентно → исход детерминирован побайтово на обоих, обе
  записи в union; потеря last_written → прогон без ошибок; миграция seq:
  старый журнал + новая правка → правка голова, порядок старых не тронут;
- **вложения**: порча блоба → AEAD-отказ → перезаливка здоровым; локальная
  порча → лестница → чужой здоровый побеждает; replace/recompress → rev+1
  едет и побеждает МОЛЧА; равный rev + разные байты → сводный диалог,
  фиксация, повторный синк ту же пару не переспрашивает, стороны сходятся;
  серверный откат байтов → сторона с записанным хешем авторазрешена;
  удаление → мини-превью (maxDeletedImageSize) с Deleted + rev+1, рамка
  «удалено» в заметке и в снимках истории; ранняя заливка: статус-бар m/n,
  обрыв импорта → следующий прогон дозаливает;
- **keyring/ключ**: ключ переживает перезапуск (ноль вводов); keyring
  очищен → запрос пароля один раз → ключ снова в keyring; недоступный
  Secret Service → сессионная деградация; ротация при стёртом sync-state →
  корректная остановка «ключ ротирован» (массовый AEAD-отказ), не «порча»;
  UI различает неверный пароль vs ротацию;
- **режимы прогона**: выход = push-only (инструментовано: ноль GET блобов,
  ноль материализаций, заливки только fast-forward); блоб, требовавший
  слияния на выходе, отложен и без потерь слит следующим полным прогоном;
  старт-синк идёт в фоне и не блокирует открытие программы; офлайн-выход =
  тихий пропуск, dirty-set переживает перезапуск;
- CLI `zametti-store sync` — тот же движок, те же тесты без UI (секреты —
  через переменные окружения для тестовой обвязки); флаги `--push-only` /
  `--full` повторяют режимы.

Критерий глазами: два ноутбука, одна заметка, правки с обоих вперемешку —
после пары синков на обоих одинаково, «проигравшие» строки достаёшь из
истории; выключил wi-fi — программа не ноет; новый ноутбук за пять минут
получает всё хранилище одним паролем.

## Правила работы

- Хранилище владельца — только чтение; все прогоны — на копиях; облачные
  тесты — только контейнеры, никаких настоящих серверов владельца.
- Ничего вне репозитория; Debug и Release; снимки Xvfb для UI-состояний.
- Каждая починка проверяется снятием — целиком; пороги — константы владельца.
- «Мои ошибки» обязательны. Измерять, а не рассуждать; сомнение — спросить.
