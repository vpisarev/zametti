# Этап 17, сессия 4: движок синхронизации с объединением журналов

Ветка `sync`, 24.08.2026, 15 коммитов поверх сессии 3. Наборы: **126 зелёных
из 127 в Debug и в Release**; красный один и давний — `FuzzOps` (отдельная
сессия по решению владельца).

Сделано всё главное из плана сессии: слияние журналов чистой функцией со
встроенной самопроверкой, dirty-set, бухгалтерия, четырёхшаговый движок
`ZStorage::sync`, предохранитель массового удаления двумя фазами,
`set-remote` и `sync` в CLI, минимальный GUI (кнопка, синк на старте и
выходе), двухдевайсный fuzz, приёмка на живом wsgidav и живой прогон на
копии хранилища владельца.

## 1. Решения владельца, принятые в этой сессии

1. **Объём**: движок + CLI + минимальный GUI (кнопка, sync on start/exit);
   окон конфигурирования WebDAV не делаем — настройка командой `set-remote`
   с двумя паролями, секреты в keyring, адрес в локальном json хранилища.
2. **`useLastRemote` — из конфига и keyring**, не из бухгалтерии: кэш
   остаётся кэшем (закрыт вопрос №3 из handoff).
3. **Вложения — presence-синк**; механизм `Zametti:Rev` (XMP) — отдельной
   сессией.
4. **Предохранитель — двухфазно**: прогон без флага задерживает удаления и
   называет список; подтверждение — повторный прогон с `allowMassDelete`;
   отказ — `declareAlive`: записи ПОВЕРХ надгробий, облако лечится, вопрос
   не повторяется, потому что изменилось состояние, а не пометка в кэше.

## 2. Новый API (коротко)

```cpp
// ZJournal — слияние отделено от диска, как и задумывалось с сессии 1:
Digest contentDigest() const;                  // идентичность НАБОРА записей
bool mergedWith(const ZJournal& other, ZJournal* out,
                MergeStats* stats, QString* error) const;
static QByteArray identityBytes(const Record&); // рамка БЕЗ укладки

// ZStorage:
bool adoptMergedJournal(id, merged, expectedBytes, error);  // с CAS-стражем
void markDirty(id);  QStringList dirtyIds();  void clearDirty(synced);
RemoteConfig remoteConfig() / writeRemoteConfig / clearRemoteConfig;
bool connectRemote(cfg, пароль-шифра, пароль-сервера, secrets, kdf, outcome);
bool useLastRemote(SecretStore&);
bool sync(const SyncOptions&, SyncReport*, QString*);   // 4 шага, отменяемо
bool declareAlive(const QStringList& ids);

// store/sync_ledger.h — SyncLedger: кэш, не истина (инвариант D);
// app/sync_controller.h — SyncController: кнопка/старт/выход, движок в
// рабочем потоке, вопросы — окну.
```

Осознанное отступление от handoff: вместо `takeDirty()` — пара
`dirtyIds()`/`clearDirty(synced)`: «взять» значило бы потерять пометки при
упавшем прогоне, а так снимается только честно досинканное.

## 3. Паранойя в бою, не только в наборах (просьба владельца)

- `mergedWith` доказывает себя НА КАЖДОМ вызове: каждая запись каждого входа
  либо в результате своим адресом, либо погашена его записью; не доказано —
  слияние не отдаётся;
- слитый журнал перед подменой файла: сериализация → parse обратно →
  пересборка КАЖДОГО слепка со сверкой отпечатка → равенство contentDigest →
  только тогда атомарная подмена; плюс CAS-страж — если редактор дописал
  запись, пока шло слияние, подмена отвергается и прогон откладывает журнал;
- материализация перечитывает записанный файл и сверяет с отпечатком записи;
- валидация локального журнала ДО классификации: битый = absence, ноль
  заливок — бит-рот не уезжает в облако; ветка «принять целиком» не верит
  ярусам на слово и проверяет «чужой ⊇ наш» по адресам;
- анти-ping-pong: равные наборы записей при разных zstd-байтах не гоняются.

## 5. Черновик для README (просьба владельца — после его правки)

### Setting up sync: a fresh store

```
zametti-store init ~/notes                # or use an existing store
zametti-store set-remote --root ~/notes --url https://dav.example/notes/ --user you
```

(A fresh store always starts with `init` — `set-remote` refuses when both the
directory and the cloud are empty: that is what a mistyped address looks
like.)

`set-remote` is the one-time setup. It asks two passwords: the *server*
password (kept in the system keyring) and the *encryption* password — asked
twice for a fresh cloud, never stored anywhere: everything is encrypted on
your machine, the server only ever sees sealed blobs. The cloud address is
remembered in the store itself (`.zametti/remote.json`), so the program syncs
on start and on exit from then on; the toolbar cloud button syncs on demand.
`zametti-store sync --root ~/notes` does the same from the console.

### Setting up sync: a new device from the cloud

```
zametti-store set-remote --root ~/notes --url https://dav.example/notes/ --user you
zametti-store sync --root ~/notes
```

Point `set-remote` at a directory that does not exist yet (or is empty): it
creates the store skeleton, inherits the store identity from the cloud
manifest, asks the encryption password once, fetches the root note right away
and reports what the cloud holds — how many notes and attachments, how large.
The first `sync` then downloads everything: notes, their full edit history,
attachments. A new laptop gets the whole store with one password.

## 5а. Матрица входов set-remote и диагностики чужого облака

(по просьбе владельца при разборе вопросов; составлено после решения №1)

### Матрица входов

| локально | облако | исход |
|---|---|---|
| хранилище (после `init`, с заметками) | пустое | первое устройство: чеканится keyfile, заливка при первом `sync` |
| пусто / каталога нет | манифест есть | бутстрап: каркас без чеканки id, id наследуется, корень материализуется, сводка облака (только суммы) |
| пусто / каталога нет | пустое | **отказ**: «looks like a mistyped cloud address or local path; run 'zametti-store init' first» — так выглядит опечатка, и огрызков-каталогов после отказа не остаётся |
| непустой каталог без метки хранилища | любое | отказ: «directory not empty» — случайную папку в хранилище не превращаем |
| хранилище с id | чужой storeId | честная остановка до единой записи (диагностики ниже) |

### Диагностики «чужого облака» — все в stderr, код 1, ни одной записи

1. `set-remote`, своё хранилище против чужого облака:
   `this cloud folder belongs to another store (<их id>), and this store is <наш id>` —
   названы оба id, видно, кто есть кто.
2. Подключение по конфигу (`useLastRemote`/страж в `setRemote`): то же плюс
   подсказка `— check sync.remoteDir` (текст подсказки устарел — адрес теперь
   в remote.json; см. §9).
3. Облако сменило принадлежность МЕЖДУ прогонами (ловит сам `sync` по etag
   манифеста из листинга): `this cloud folder now belongs to another store
   (…) — refusing`.
4. Хранилище с заметками, но без идентичности (легаси) против облака с
   манифестом: `this store has notes but no identity, and the cloud belongs
   to store … — bootstrap into an empty folder instead`.
5. Манифест свой, keyfile чужой (мешанина в облаке руками): `the cloud
   keyfile belongs to store …, not …`.
6. Смежные стражи той же двери: `the cloud manifest is unreadable: …`;
   `the cloud was written by a newer version of the program — update this
   one`; `wrong password, or the keyfile is corrupted: …` (последние два
   неразличимы по построению AEAD, о чём сказано прямо).

## 7. Долги, названные вслух

1. ~~Бутстрап требует руками создать каркас~~ — ЗАКРЫТО в этой же сессии по
   разбору вопросов с владельцем: `set-remote` на пустом или несуществующем
   каталоге сам заводит каркас (без чеканки идентичности — она наследуется из
   манифеста), скачивает и материализует корневую заметку и печатает сводку
   облака (только суммы: заметки, вложения, объём). Правило строгое:
   содержательна РОВНО ОДНА сторона; «пусто с обеих» — отказ со словами про
   опечатку (решение владельца: так выглядит неверный адрес или путь, и молча
   чеканить новую пару хранилище+облако значило бы её спрятать; новое
   хранилище начинается с `init`). Отказ не оставляет огрызков. Вход оформлен
   статическим `ZStorage::initFromRemote` — его же позовёт диалог первичной
   настройки в самом zametti (и на Android, где консоли нет); диалог — в
   очередь.
   Попутно clang-tidy вскрыл спящий дефект recompress: `--quality`
   игнорировался из-за повисшего if (починен отдельным коммитом).
2. **Материализация во время прогона не обновляет строки списка до конца
   прогона** (refreshNote — по завершении). Открытая заметка живёт
   external-путём и обновляется сразу.
3. **Гонка «файл материализуется, пока редактор пишет тот же файл»** сжата
   до микросекунд повторной сверкой хеша, но строго не исключена: пара
   «файл+журнал» редактора не атомарна относительно движка. Названо в
   комментарии материализации; лечение — сигнал редактору при синке, если
   когда-нибудь проявится.
4. **Ранняя фоновая заливка вложений при импорте** (статус-бар «m/n») — не
   делалась: вложения едут батчем при синке.
5. **`sync.intervalMinutes`** (периодический синк) — не делался, как и
   договаривались.
6. **Проверка push-only на выходе живым окном** не сделана: убить окно под
   Xvfb штатно (WM_DELETE) нечем без xdotool. Логика покрыта набором
   `checkPushOnlyMode`; глазами стоит проверить владельцу одним выходом.
7. **wsgidav-приёмка держит стенд на каждый прогон набора** (~5 с);
   пропускается громко, если uvx нет.

## 8. Мои ошибки

1. **Я снова оставил след вне репозитория**: CLI-прогоны писали бухгалтерию
   в настоящий `~/.config/zametti/` (файл `sync-state-…json`), а первый
   GUI-прогон шёл без подмены `XDG_CONFIG_HOME` — повезло, что `state.json`
   владельца не перезаписался (окно умерло до записи). Файл убрал, все
   последующие прогоны — с подменённым каталогом. Урок тот же, что в
   сессии 3 с keyring, и это тревожно: «куда пишет процесс» надо проверять
   ДО запуска, а не после.
2. **Моё первое снятие починки оказалось пустышкой** — ровно то, о чём
   предупреждал handoff. «Снял» анти-ping-pong, а тест остался зелёным:
   ветка выходила через `continue` раньше заливки, и снятие ничего не
   меняло. Честное снятие (вся ветка целиком) дало 3 красных. Правило «если
   снятие не покраснело — сперва не верь снятию» подтверждается второй
   сессией подряд.
3. **Матрица движка нашла четыре моих дефекта разом**: перевыдача etag
   глушила лечение absence; задержанные предохранителем удаления не
   переоценивались следующим прогоном (пометку стирала финальная чистка);
   выравнивание ВОСКРЕШАЛО БЫ ещё не материализованное удаление (файл при
   надгробии-голове надо сравнивать с последним слепком); нулевой бюджет
   выхода не отсекал ничего (`>` вместо `>=`). Все четыре — до боя, ценой
   одного прогона набора.
4. **Дымовой стенд я собрал с негодными id** (буква `u` вне алфавита) — и
   полчаса смотрел на «Untitled» вместо трёх заметок. Алфавит id надо было
   проверить до, а не после.
5. **Забыл, что окружение шелла не живёт между вызовами**: сгенерированный
   `ZAMETTI_SYNC_KEY` потерялся вместе с шеллом, и облако осталось запечатано
   ключом, которого больше нет. Пересобрал стенд с ключом в файле.
6. **Мои прогоны выбили владельцу диалог «unlock keyring»** — CLI лез в
   keyring при заданном пароле среды. Починено правилом: секрет в среде =
   headless, keyring не трогается.
7. **В сообщение коммита я вписал «129 зелёных», не посчитав** — настоящее
   число 126 из 127. Поправил amend-ом, но урок обиднее правки: числа в
   отчётах пишутся только с прогона.
